最新设计约定：UI 审批与后台派工（2026-09-24）

后续开发方向，尚未实现。本节优先于下文历史基线中冲突的语言、角色、审批入口与部署描述。

  • 后续开发以本节和云端协作设计方案为指导：直接扩展现有 GameCLIServer，服务端采用 Node.js + TypeScript，负责审批、依赖、租约和派工；不再新建 Python 编排服务。新增模块使用 TypeScript，现有 JavaScript 逐步迁移。C#/.NET GameCLI 保留，负责本地 Agent 执行，JIRA 仍为业务状态唯一可信来源。技术方向已确认，新增能力待实现。
  • Codex 对话负责需求讨论与修改，扩展 UI 完整展示需求。人工点击“批准此版本并启动流程”，绑定需求版本、文件哈希与真实批准者，服务成功写入 JIRA 才显示已批准。
  • 主任务需求附件先上传并核验，最多三次；之后云端选择空闲且具备 PM 能力的 GameCLI，由其内部 PM Agent 按交付标准拆分、通过确定性适配代码建单。
  • GameCLI 回报真实单号及计划版本，云端重新检查 JIRA 的父子关系、依赖、附件及版本，再自动寻找空闲专业 GameCLI 启动依赖就绪任务，无需建单后重复下令。人工抽检、最终验收及发布门禁继续保留。
  • GameCLI 使用后台常驻主进程，通过 WebSocket 注册节点、上报容量、心跳续租、接收任务并确认、回传进度和接收取消指令；每项任务独立 Agent 会话，完成后继续等待。HTTP 用于需求提交、详情查询、文件上传、最终结果提交与断线核对；一次性命令仍保留。HTTP 长轮询不列入首版必做项。
  • 派工必须先在 JIRA 持久化分配与租约，再通知节点；有效租约核验与接单确认后才启动 Agent。重复消息不得重复启动，结果提交必须幂等；断线重连核对未结束执行，失联不立即重派，旧租约代次不得推进任务。WebSocket 发送成功不等于业务成功。
  • 关闭看板或结束聊天不停止后台执行端；暂停接单不等于取消当前任务。首版单调度实例支持多执行节点，不承诺多活互斥。
  • 本期不接入、调用 Unity CLI，也不以 Unity 环境作为启动前置条件；聚焦 UI 审批、PM 建单、Agent 启动、状态回传和 JIRA 核验。未运行的开发／验收不能标为完成。
  • 当前 Codex 存在 MCP App UI 和侧方面板实现，但账号开关、自建组件、审批交互仍需最小示例实测。

完整方案：云端编排与 Codex 协作平台设计方案 v1.3。

流程修订与已实现阶段：新增独立 Design 策划角色，职责以 多 Agent 流程指导纲要为准。当前 Orchestrator 已提供 start/status/approve/resume/revise 命令，由 Codex 对话提供文档并调用，面板仅保留运行监控：文档交给 Design，用户确认需求版本后启动独立 PM Agent，通过受控工具创建美术、程序和 QA 单据。执行状态与审批保存在 JIRA issue property；制作、QA 执行调度及原生 JIRA 状态迁移尚未实现。详见 使用说明与当前限制。下文旧 PM 分析职责由此修订替代。

1. 项目概述

1.1 目标

构建一条以 JIRA 为控制平面、Orchestrator 为调度核心、4 个 AI Agent 为执行角色、Unity CLI 为确定性验证器的游戏开发自动化流水线。

将策划需求自动转化为可执行任务，由 AI 完成需求分解、JIRA 建单、美术生成、代码实现、Unity 编译测试、QA 验收，并通过人工门禁控制合并与发布。

1.2 核心原则

确定性包围不确定性。状态机、幂等、重试保证流程可靠；LLM 只负责内容生成，不负责流程决策。
原则含义
JIRA 是唯一事实源JIRA 是唯一可信来源：任务状态、审批、重试次数、执行记录和幂等键统一保存在 JIRA；调度器每次从 JIRA 读取并写回，不维护独立状态数据库
JSON 契约交互Agent 之间不直接对话，通过结构化输出协作
人工只做门禁需求确认、美术抽检、合并发布，其余全自动
CLI-first 起步单 CLI + 子命令快速跑通闭环，后续再服务化
先桩后真JIRA 从 MVP 起真实接入；其他外部依赖先用桩函数，再逐个替换

1.3 最终形态

策划需求
  → PM Agent 拆需求建 JIRA
  → Orchestrator 调度
  → Art Agent 产资源入库回写 JIRA
  → Dev Agent 编码开 PR
  → Unity CLI 确定性验证
  → QA Agent 验收
  → 失败自动修复
  → 成功人工门禁
  → 合并发布

3. 角色划分

3.1 逻辑 5 角色，工程 4+1

逻辑上是 5 个角色：4 个业务 Agent + 1 个 Orchestrator。
工程实现上推荐：4 个 LLM 业务 Agent + 1 个确定性编排服务。Orchestrator 不是自由发挥的 LLM，而是状态机。
角色类型是否 LLM核心职责
PM Agent业务 Agent是策划文档分解、JIRA 建单、验收标准、美术 Manifest
Art Agent业务 Agent是美术资源生成、入库、回写 JIRA
Dev Agent业务 Agent是编码、开 PR、跑 Unity CLI、修复
QA Agent业务 Agent是验收、失败分类、回写 JIRA
Orchestrator调度器否（或仅异常决策）状态机、调度、重试、幂等、人工门禁

3.2 PM Agent（产品经理）

CLI 已改为插件注册结构：所有插件实现 ICLIPlugin，所有 CLI 命令实现 ICommand；Program 仅组装插件，PluginHost 负责统一分发与启用检查。通过 GameCLI plugins list / enable / disable 管理插件。PM 与 Unity 已有命令，Art、Development、QA、Jira、Orchestrator 插件已注册但业务 CLI 命令尚待实现。启用偏好保存在 ~/.gamecli/plugins.json，仅控制后续 CLI 调用，不是 JIRA 工作流状态。当前为编译内注册插件，未实现 DLL 热加载。

PM 分页的第一个功能是 JIRA 连接配置：配置 JIRA Address、Project Key 与 Access Token，统一采用 Bearer 认证；Project Key 保存为默认目标项目配置，兼容旧配置为空，修改它不改变服务器凭据归属，再开展需求分析与任务管理。当前 Editor 已实现配置保存与连接测试；连接元数据保存在用户目录 ~/.gamecli/jira.json，凭据单独存入 Windows 凭据管理器，不写入工程。连接测试通过当前用户接口验证身份，不代表已验证项目写入权限。JIRA 始终是工作流数据的唯一可信来源，独立 CLI 已提供 GameCLI pm --analyze：启动 Codex App Server、加载角色 Skill、实时接收进度并校验结构化只读草案。Orchestrator 页每秒刷新本机 GameCLI 活跃会话与执行任务数量，展示角色、工程、会话 ID 和耗时；临时进程发现记录不保存工作流状态。当前 CLI 已提供最小 JIRA 建单：通过 GameCLI jira --create 在配置的 Project Key 下创建 Task 并返回真实编号和链接；PM 面板的手工建单表单已移除，保留连接配置和测试；请求结果未知时不自动重试，需先核对 JIRA。AI 草案自动拆单、扩展字段与多角色自动编排仍待实现。

4. Orchestrator 设计

4.1 核心职责

Orchestrator 的核心是：用确定性的状态机来驱动不确定性的 AI Agent。

  1. 监听 JIRA Webhook 或轮询 JIRA
  2. 读取任务状态和字段
  3. 决定下一步调用哪个 Agent
  4. 组装上下文，传入任务包
  5. 设置超时、重试、幂等键
  6. 写回 JIRA
  7. 控制人工门禁
  8. 记录全链路 Trace

4.2 技术选型

模块实现路线约束
CLIC# / .NET 8 控制台工程复用已创建的 GameCLI.csproj，命令层保持轻量
编排器C# 纯函数状态机与异步任务调度JIRA 是唯一可信来源，不引入第二套权威状态库
数据契约C# DTO、System.Text.Json 与显式校验结构化输入输出，缺失或无效数据不得推进流程
外部集成C# JIRA 客户端与 Unity 进程执行器超时、重试、幂等执行记录统一关联 JIRA
Skill标准 SKILL.md放在 game-cli/，供对应 AI 工具加载
统一使用 C# 开发 CLI、调度器、集成与验证工具；Skill 保持 Markdown 指令格式。MVP 使用 C# CLI + JIRA + 纯函数状态机。

4.4 幂等与重试

幂等键

{issue_key}:{from_status}:{to_status}:{content_hash}

幂等键与执行结果统一记录在 JIRA。执行副作用前读取 JIRA 中的记录，完成后回写结果；崩溃恢复时先核对目标系统中的已有产物，再决定重试或补写 JIRA。JIRA 不可用时暂停推进流程，不使用本地状态代替 JIRA。

重试策略

重试配置使用 JSON，由 C# DTO 读取和校验：

{
    "max_attempts": 3,
    "backoff": "exponential",
    "retryable_errors": [
        "NETWORK_TIMEOUT",
        "RATE_LIMITED",
        "UNITY_CRASH",
        "CI_INFRA_ERROR"
    ],
    "non_retryable_errors": [
        "SPEC_INVALID",
        "AUTH_FAILED",
        "HUMAN_REJECTED"
    ]
}

错误分类处理

错误类型处理方式
可重试（网络超时、限流）指数退避自动重试
可修复（代码错误、资产错误）触发对应 Agent 修复
不可重试（需求无效、权限失败）转人工

6. 统一 CLI 设计

6.1 从多 CLI 到单 CLI

原来 5 个 CLI 的问题是：用户要记住 5 个命令、5 套参数、5 套环境变量、5 套退出码约定。合并成一个 CLI + 子命令，门槛立刻降下来。

图 6-1 gameai 命令树

当前已实现最小命令 GameCLI unity --ping --project <Unity工程路径> --format json：通过命名管道连接真实 Unity Editor，返回 pong、工程路径、Unity 版本、PID 和 UTC 时间。该命令验证桥接连接，不代表 JIRA 或游戏功能验证通过。完整流水线命令仍为规划。

Unity Editor 已提供 Tools > GameCLI > Window 安装窗口：异步构建/重装 CLI 到当前项目的 Library/GameCLI，显示日志并支持取消；分页 Toolbar 按 Orchestrator、Design、PM、Art、Development、QA 展示命令分类。Design 为策划命令入口，目前显示尚未实现提示；Unity 分页及其命令开关列表已移除，终端 unity --ping 与既有命令启用设置仍保留，关闭的路由返回 command_disabled。设置按用户和项目保存在 EditorPrefs，不属于 JIRA 工作流状态。PM 页提供 JIRA 连接配置、Project Key、保存与测试，手工 Task 创建入口已移除；CLI 建单能力保留，AI 自动拆单等后续业务流程仍待实现。PING 通过终端执行。需要可用的 .NET SDK；不修改系统 PATH。

7. Skill 体系设计

Skill 是 Agent 的"原子能力"。Agent 负责决策"做什么"，Skill 负责"怎么做"。
Skill 只做单一职责；每个 Skill 有明确输入输出契约；确定性 Skill 与 LLM Skill 分离；Skill 可独立测试、可被多个 Agent 复用。

7.2 标准 Skill 契约

Skill 使用标准目录与 SKILL.md 文件。文件以 YAML frontmatter 开头，包含 name 和 description，正文定义输入、职责、流程约束与输出。Skill 是操作指令，不是可执行程序，也不等于已实现的 Agent 或 CLI。

---
name: gameai-pm
description: 拆解游戏需求并定义 JIRA 任务与验收标准；用于 PM Agent。
---
# PM Agent
读取需求与 JIRA，拆分任务、依赖和验收标准，返回结构化结果。

策划、项目管理、美术、程序、测试验收五个业务 Agent 各有独立角色技能；编排器有独立技能，仍按确定性状态机执行。所有角色共用 gameai-common、gameai-jira 和 gameai-unity，按需读取其 SKILL.md。

7.3 Skill 发现与加载

加载器扫描技能目录中的 SKILL.md，先读取 name/description 选择技能，再加载正文及其引用。标准技能统一放在 com.oathx.gamecli/game-cli/。可将其中 gameai-* 技能目录复制或安装到目标 AI 工具的技能根目录，保持目录名称和同级关系；同时携带所引用的公共技能，编排器还需要五个角色技能。复制全部十二个目录可保留完整引用。gameai-cli-development 用于本工程开发约定，由仓库 AGENTS.md 引用，不增加业务 Agent 角色。当前未自动安装到任何 AI 工具。可选 scripts/ 用于真实的确定性工具，references/ 用于详细契约，assets/ 用于输出模板，按需添加。

技能保持单一职责。策划与项目管理引用独立的单据编写技能，宿主显式加载依赖。单据标题和描述使用中文，按列表展示开发内容、业务规则与待执行测试用例；未决内容仅在对话处理，不进入单据正文。测试用例使用目录层级，条件、操作和预期逐行展示。严格限定移动触屏平台。策划结果必须回到当前 Codex 对话反复沟通，用户明确确认完整需求版本后，才由项目管理创建对应专业子任务并记录依赖；确认前只保存主任务草案，恢复复用原单据，制作、编码和测试执行仍保留审批。配置表字段、代码标识符、路径及单据编号和链接保留必要原文。流程快照存于单据属性，不出现在描述中。

后续默认采用需求主任务及美术、程序、验收子任务结构。专业建单必须使用真实子任务类型和父任务字段，保留独立的执行依赖；恢复核对父任务，不重复创建。既有独立单据通过转换保留原编号。

7.5 Skill 编写规范清单

  1. 每个技能目录与 frontmatter name 一致，使用小写字母和连字符，入口统一为 SKILL.md。
  2. description 明确适用任务；正文定义职责、输入、输出和真实约束，不把规划能力描述为已实现工具。
  3. 结构化 JSON 输出遵循 gameai-common；缺少证据、工具或配置时报告阻塞。
  4. JIRA 是状态、审批、重试和执行记录的唯一可信来源，不创建本地状态数据库。
  5. 业务角色不直接调用其他 Agent；编排器按已定义的状态迁移负责调度。
  6. 外部写入和人工门禁遵守任务授权；Skill 文件本身不扩大权限。
  7. 有副作用的操作使用 JIRA 执行记录并核对结果；记录 Trace 和错误分类。
  8. 按需添加 scripts/、references/、assets/，不要求每个技能都有空辅助目录。

10. Unity CLI 确定性要求

10.1 固定项

  • Unity 精确版本，例如 2022.3.XX
  • Docker 镜像 digest
  • Packages/manifest.json 和 packages-lock.json
  • 资产 Hash
  • 代码 Commit
  • 随机种子
  • 构建脚本
  • 输入 Hash：需求 Hash + 资产 Hash + 代码 Commit
  • 输出：测试报告、Build Hash、日志、截图

10.2 执行命令

docker run --rm \
  -v $PWD:/workspace \
  unity-runner:2022.3.XX \
  Unity -batchmode -nographics -quit \
  -projectPath /workspace/Game \
  -executeMethod Automation.CI.RunAll \
  -logFile /workspace/Logs/ci.log

10.3 确定性定义

确定性 = 相同输入、相同环境、相同版本，得到相同的测试结果和可验证产物，而不是 bit-for-bit 完全一致的二进制。

12.5 关键原则

  1. 先桩后真：JIRA 从 MVP 起真实接入；其他外部依赖先用桩，链路先通
  2. 接口先行：通过统一 JiraClient 读写 JIRA，测试替身仅用于隔离测试
  3. 状态唯一源：JIRA 是唯一可信来源；任务状态、审批、重试和执行记录均从 JIRA 读取并写回
  4. 契约优先：Agent 运行时使用 C# DTO 和 System.Text.Json，并显式校验输入输出；Skill 用 SKILL.md 定义职责和契约
  5. CLI 薄：命令层只解析参数，逻辑在 Agents/ 和 Core/
  6. 可回放：workspace/ 里所有产物可查、可复现
  7. 不提前优化：不上分布式调度框架、不上 K8s、不上多进程

14. 总结

本方案以 JIRA 为控制平面，Orchestrator 为调度核心，4 个 AI Agent 为执行角色，Unity CLI 为确定性验证器，形成完整闭环。

14.1 核心架构

策划需求
  → PM Agent 拆需求建 JIRA
  → Orchestrator 调度
  → Art Agent 产资源入库回写 JIRA
  → Dev Agent 编码开 PR
  → Unity CLI 确定性验证
  → QA Agent 验收
  → 失败自动修复
  → 成功人工门禁
  → 合并发布

14.2 核心原则

原则说明
确定性包围不确定性状态机、幂等、重试保证流程可靠；LLM 只负责内容生成
JIRA 是唯一事实源所有状态、执行记录和产物链接统一写回 JIRA；不维护第二套状态源
JSON 契约交互Agent 之间不直接对话，通过结构化输出协作
人工只做门禁需求确认、美术抽检、合并发布
CLI-first 起步单 CLI 快速跑通闭环，后续再服务化
先桩后真JIRA 真实接入，其他外部依赖先用桩函数
Skill 越确定，流水线越稳Agent 负责"想"，Skill 负责"做"

14.3 最终形态

5 个逻辑角色，1 个 CLI，4 个 Agent，1 个调度器，1 条闭环。
gameai start --spec ./docs/game.md --project GAME 即可启动全流程。

专业交付门禁实现补充（2026-09-23）

当前已实现专业调度：美术交付并抽检完成后启动程序，程序交付校验完成后启动验收；没有美术需求时直接开发。主子任务归属与执行依赖分别维护。

  • 使用 orchestrator --gates 检查前置任务；使用 orchestrator --dispatch 启动满足依赖的专业代理。两者均指定需求主任务与本地工程目录。
  • 当前需求版本必须获批。前置子任务原生状态为完成，并且交付文件存在、哈希一致、检查证据齐全、输入版本有效，才能放行下游。
  • 实际文件与报告落在工程内；执行及交付清单记录在子任务属性 gamecli.delivery.v1，JIRA 继续作为唯一可信状态来源。
  • 代理提交不等于批准。美术抽检完成后再次调度；程序交付通过校验后自动完成子任务并启动验收，不增加程序人工审批；最终验收由用户完成。上游返工或版本变化使下游旧交付失效。
  • 当前串行、按调用推进，不常驻监听；缺少美术工具、运行环境或测试证据时阻塞，不伪造成功。跨机器并发、自动缺陷闭环和跨需求变更审批仍属后续工作。

单一职责规范：game-cli/gameai-task-delivery/SKILL.md；详见 docs/agent-workflow-development-guide.md。

集中协调服务与通知通道

团队模式采用 Node.js GameCLIServer 接收 JIRA Webhook，通过固定 WebSocket 协议连接 C# GameCLI 客户端。JIRA 继续作为需求、审批、依赖和交付的唯一可信来源；事件缓存不是业务状态库。

当前已实现局域网免认证项目事件订阅、JIRA 回调令牌校验、心跳、重连、有限补发与重新核对提示。集中派工、执行租约、自动核对及结果回写仍待实现；不能将状态广播直接解释为所有客户端的执行授权。

服务源码位于 GameCLI~/GameCLIServer，方案与部署见 协调服务设计。客户端使用 orchestrator --connect 连接，现有单机调度命令保持原有门禁。

ART 只读联调已提供 orchestrator --art-probe：事件服务连接、JIRA 子任务核对、真实 Art 会话启动和独立诊断记录回写；不制作资源、不改变审批或单据完成状态，正式集中派工仍待实现。

已实现：Unity 面板的 Orchestrator 页面提供当前工程本机 Agent 任务列表；各专业角色页面按角色显示 JIRA 单号、工作内容、启动或工作状态、正式执行或只读联调模式、耗时及会话详情。每秒读取临时进程元数据，不轮询 JIRA；该看板不代表跨机器团队状态，也不作为任务完成或审批依据。顶部说明区域不滚动，列表紧随其后；列表与 Output 独立滚动，通过下方分隔条调整高度并保留比例。

需求产生遵守 gameai-requirement-discovery 专项技能：先调研同类成功或成熟产品并记录来源，再生成完整推荐草案；全部重要澄清题在当前 Codex 对话一次展示，输入者一次完成选择后统一修订，最后确认整份版本。当前独立 Design 禁用联网，由当前对话助手先检索并提供可核验摘要。不得逐题触发修订，也不能把推荐或答题视为批准。

需求建单门禁已实现：人工确认后，先上传对应版本 HTML 并核验文件哈希，再启动项目管理代理分拆和创建子任务。上传最多三次，失败停止；次数与回执保存在 JIRA，恢复不清零，上传结果不明时先核对附件。

较大的工作流快照以带 SHA-256 校验的 gzip-base64-v1 封装无损保存于同一个 JIRA 属性；小快照和已有明文属性保持兼容。解压大小上限 1MB，压缩后仍须满足 32000 字节限制，超过时停止，不截断需求、审批或执行历史。

PM 按独立交付标准输出同角色多任务，以 depends_on 表达真实依赖并按拓扑顺序发布。新增 orchestrator --replan，仅迁移尚未开始、无交付记录的已发布计划；PreviousPlan 保留旧计划，原子保存新计划后复用旧任务编号并补建其他任务，最终刷新全部单据依赖编号。执行中断使用 resume，不重新拆分；调度仅在 tasks_created 后允许。当前每计划最多 20 项，显式迁移一次。
