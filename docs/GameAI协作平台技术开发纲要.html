1. 设计目标与约定优先级

将已审阅的单项目 Track 小样建设为真实协作工作台：在 Codex 讨论需求，在 Track 审阅并人工批准，GameCLIServer 保存业务事实和集中调度，后台 GameCLI 启动专业 Agent，最终回收交付与验收证据。

技术基线：React + TypeScript + Ant Design；Node.js + TypeScript；PostgreSQL；C#/.NET GameCLI。 已完成 Ant Design 工作台、PostgreSQL 24 张业务表及测试数据入库，Track 读取实际数据库；正式身份、审批写接口和集中派工尚未实现。字段与维护说明见 数据库设计与入库说明。
  • 本期为单项目工作台：删除多项目导航与项目切换；服务配置固定项目上下文，数据中保留项目标识用于防止跨工作区误关联。
  • 新架构以 PostgreSQL 为唯一业务数据来源，通过 GameCLIServer 读写。JIRA 不再是新系统运行前提，不做双向同步或双主写入。
  • 现有 JIRA 实现属于迁移前基线，在明确切换前保持原有行为；不能因本文存在就让旧命令改写新系统。
  • 本文优先于旧云端方案中关于 JIRA 唯一来源、多项目界面和待选前端库的条款；旧代码及历史记录不在本次文档工作中删除。
  • 本期不接入 Unity CLI、不执行真实 Unity 验收；正式发布和最终人工验收保留独立门禁。

4. 前端技术与页面设计

选定 React + TypeScript + Ant Design，采用组件级导入及统一主题。保留现有构建入口，先扩展当前 esbuild 流程支持 TSX 和样式打包；不因引入 React 同时重写服务端或强制切换构建工具。具体稳定版本在接入时核对兼容性并写入锁文件。

不引入 Ant Design Pro 整套后台模板；首版不安装图表库。使用深色与紧凑主题、small 控件、英文列表标题和中文业务内容。

4.2 状态与交互

  • 页面必须区分加载、空结果、无权限、请求失败、数据过期；断线保留最后快照并显示时间，不能伪装为零任务。
  • 批准必须由用户点击确认，处理中禁止重复提交；成功后显示服务端审批回执。失败保留文档并给出原因；响应丢失先查询原操作结果。
  • 弹窗、下拉和抽屉限制在组件根容器内，验证窄侧栏、键盘焦点、滚动和宿主沙箱样式。
  • 小样中的身份选择仅供演示；正式系统身份来自服务端认证会话，不能通过下拉框切换管理员。
  • 完整需求 HTML 采用隔离、禁脚本阅读视图，禁止直接向应用根插入未可信 HTML；审批按钮属于可信应用界面。
  • 窄屏优先隐藏次要列并放入详情，避免整页横向滚动；真实列表必要时保留自己的横向滚动。

6. PostgreSQL 数据模型

核心关系使用关系表、外键和唯一约束；可扩展内容使用 JSONB。需求发布后版本不可覆盖，审批绑定版本记录与对应文件字节哈希。

逻辑表主要内容关键约束
projects单项目配置、默认工作区首版只启用一个项目，不提供项目创建或切换 UI
users / roles / permissions / user_roles人工身份与授权有效权限由服务端计算；项目范围明确
agents / agent_grants / workers角色实例、执行节点、读取/任务写入授权、能力与容量Agent 与工作站分开建模；节点身份不可冒用
requirements / requirement_versions需求标识、递增版本、正文、结构化交付标准、文件引用及哈希同需求版本唯一；提交审阅后内容不可改写
approvals审批对象、版本、批准/退回、人工主体、时间与原因不接受 Agent 身份批准；重复操作返回同一回执
plans / plan_versionsPM 拆解草案、批准需求版本、交付项映射每主任务计划发布串行；一次只激活一个计划版本
tasks / task_dependencies主子任务、角色、交付标准、依赖版本同项目父子关系；禁止自依赖和环；计划发布前完整验证
executions / task_leases执行编号、任务、节点、代次、状态、截止时间、输入版本同任务最多一个未解决执行；旧代次不能推进结果
artifacts / artifact_links文件存储键、哈希、字节数、类型、归属版本文件校验后才可引用；代码记录提交哈希
comments / audit_events结果摘要、人工与系统操作、操作者、关联版本结果评论按执行和操作唯一；审计通过应用追加
idempotency_records / outbox_events幂等请求及响应、事务内待发送事件幂等键按主体和操作限定；同键不同请求拒绝
  • 审批、任务状态和执行租约不只放进一个大 JSON 文档；可索引字段应明确列出。
  • 任务领取使用事务与行锁；唯一约束作为最后防线。依赖成环检查在同一计划发布锁内完成。
  • 过程日志放文件并轮转；数据库保存摘要、索引和定位。心跳在线缓存可在内存，执行所有权必须持久化。
  • 附件保存于配置的数据目录，使用服务端生成的存储键；数据库和文件存储分别备份并校验引用一致性。
  • 原始 HTML 文件哈希基于实际字节计算；JSONB 不承担保留原始文件格式的职责。

7. 身份、权限与信任边界

必须区分人工用户、Agent 专业角色、执行节点和服务自身。早期免认证通知转发可保留为旧功能，但不能直接用于新的审批和远程写入接口。

主体读取状态/文档审批需求业务写入权限管理
策划人工用户允许获授权后允许提交修订、填写退回原因；不直接改执行状态默认禁止
PM / Art / Development / QA 人工用户默认允许默认禁止首版面板默认只读禁止
项目管理员允许不因管理员身份自动获得审批权，可另授策划审批角色用户与节点管理允许
Design Agent按任务范围禁止提交需求草稿或新修订版本禁止
PM Agent按批准需求和任务范围禁止提交交付项拆分计划，由服务验证发布禁止
Art / Development / QA Agent按任务及依赖产物范围禁止仅提交所分配执行的产物与证据禁止
  • 有效 Agent 写权限 = 项目授权 ∩ 角色能力 ∩ 当前任务范围 ∩ 有效执行代次；面板只读不等于执行端无法提交自己的任务成果。
  • 未持有有效租约、被撤销授权或引用旧版本的写入被服务端拒绝。拒绝中记录原因，不靠隐藏按钮实现安全。
  • 首版建议使用服务端用户会话与可撤销节点凭据；管理员初始化账号，人工以自己的会话批准。连接数据库的账户不得复用为用户身份。
  • MCP 本地进程不能替所有用户使用一个管理员凭据。普通模型工具不暴露可批准需求的入口；审批工具应限定为 UI 调用，并再次校验真实用户会话和版本。
  • 若当前宿主无法可靠传递审批身份，应将审批标为未支持或使用经授权的浏览器登录流程，不能把模型传来的 approved_by 当作身份凭据。
  • 权限变更记录审计；取消读取授权后，服务停止推送并要求前端清除对应视图。已经开始的执行按取消/核实流程处理，不直接释放后重派。

8. 需求到验收的完整流程

  1. 需求讨论：在 Codex 描述需求；Design 先参考成功项目同类功能，再产出草案。需决策事项集中询问，避免逐项弹窗。
  2. 文档生成：沿用策划技能，包含目标、综述、线框、配置表、操作交付标准和美术表现需求；本地输出到仓库相对路径 app/desgin/。
  3. 提交版本：GameCLI 上传草稿内容与文件，服务器保存不可变审阅版本。当前 HTML 文件不能因后续覆盖而改变已审批版本。
  4. 人工审批：Track 显示完整指定版本，用户批准或退回。审批事务检查权限、版本及哈希并返回回执。
  5. 文档发布门禁：确认服务器已持久保存批准文件、长度与哈希正确，再进入 PM 队列。上传/发布失败最多尝试三次，总次数持久化，服务重启不清零；三次失败明确阻塞，可经人工授权新建重试操作。
  6. PM 接单：服务器选择可用且有 PM 能力的 GameCLI，先写分配与租约，再发通知；PM 只处理该批准版本。
  7. 计划发布：PM 按交付标准拆成可验收子任务，列明角色、输入、产物、验收条件及依赖。服务器检查覆盖、重复、循环及版本后，在事务中发布主子任务和计划。
  8. 自动派工：满足批准、文档、依赖和资源条件的任务进入可领取状态；选择能力匹配、授权有效、容量足够的节点。
  9. 专业交付：GameCLI 启动独立 Agent 会话，回传进度、日志和产物；服务校验执行代次及输入版本，将结果追加到任务评论。
  10. 解锁与验收：美术产物验证后解锁对应程序任务，基础逻辑可并行；QA 验证精确代码和资源版本，失败产生关联修复任务。
  11. 完成：必要子任务及 QA 证据通过后等待人工最终验收；合并和发布需要独立授权。
新系统不再“上传到 JIRA 后建单”，改为“服务器保存并核验需求附件后发布内部子任务”。保留先附件、后三次失败阻塞、再 PM 拆分的业务意图。

9. 状态机、版本和依赖

分别维护需求、任务和执行状态，避免用一个状态字段表示所有阶段。

对象主流程异常或分支
需求版本草稿 → 待审批 → 已批准 → 文档已核验 → 已发布退回修改生成新版本；发布失败阻塞；旧批准版本保留
任务待门禁 → 可执行 → 已分配 → 执行中 → 待核验 → 已完成依赖阻塞、失败、取消中、已取消、待核实
执行已创建 → 已确认 → 运行中 → 结果已提交 → 已接受超时、拒绝、失败、取消中、停止待核实
计划版本草案 → 校验通过 → 已发布 → 被新计划替代校验拒绝；历史计划只读
  • 需求版本、计划版本、任务输入版本、执行代次、代码/美术版本和验收版本分别记录，不能只显示一个 v1.0。
  • 需求变更先做影响分析；正在执行的任务不静默切换输入。受影响的旧交付暂停下游放行，决定取消、重做或继续保留旧计划。
  • 依赖以具体产物和交付项为单位；不强制全部程序等待全部美术，禁止仅按角色排成一条串行队列。
  • PM 发布前校验每项交付标准都被覆盖；子任务必须可独立验证，不能只建“全部美术”“全部开发”“全部 QA”三个大任务。
  • 每次结果提交都有任务评论摘要，包括执行编号、输入版本、产物、验证证据、失败原因和下一步。运行日志不等于交付证据。

10. 接口、消息与并发派工

通道建议契约说明
HTTP/api/v1/requirements、/versions、/approvals提交与读取需求；审批必须带版本、哈希、幂等键和真实会话
HTTP/api/v1/tasks、/plans、/artifacts、/executions/{id}/result计划、文件和结果使用校验后的命令接口，不开放任意字段修改
HTTP/api/v1/track/snapshot、/events?after=…初始快照与断线补齐；限定项目、分页和日志范围
WebSocketworker.register / heartbeat / dispatch / accepted / progress / cancel执行端常驻双向通道；事件版本、消息 ID、执行 ID、代次与关联 ID 明确
MCPgameai_track_open / snapshot / detail 等薄工具保留现有只读入口；写工具后续逐项定义可见性和权限，不提供通用 SQL 工具

10.1 领取与可靠发送

  1. 服务端事务锁定候选任务及节点容量记录，核对门禁、权限、有效依赖和空闲槽位。
  2. 同一事务写执行记录、租约代次、占用容量以及 outbox 待发送事件；失败则整体回滚。
  3. 事务提交后发送 WebSocket 指令；发送成功不等于接单成功。节点以执行编号去重，确认后启动会话。
  4. 丢失确认时重新发送同一指令，不生成新执行。完成结果提交使用幂等键，同键不同内容拒绝。
  5. 收到结果后事务核验租约、状态和版本，登记结果、评论及下一步事件。重复提交返回已有回执。

10.2 恢复规则

  • 心跳用于感知在线与续租；租约过期但执行可能仍在写文件时标记待核实，不立刻转派。
  • 节点重连上报未结束执行；服务器查询持久记录，确认旧执行已停止或副作用已核实后才能创建新代次。
  • 取消必须有节点响应或核实证据。暂停接单不取消正在执行的任务。
  • 数据库不可用时停止批准、派工和接受权威结果；客户端可保留未确认结果，恢复后以同一幂等键提交。
  • 文件上传、数据库事务和 Agent 外部动作不能靠一个数据库事务覆盖；采用分阶段状态、幂等回执及补偿/核实。
  • 首版仅单调度实例，支持多执行节点；多实例调度另行设计，不依赖“单实例”跳过数据库互斥。

看板通过宿主桥接获取真实快照。事件通知不可用时可对本服务进行有界刷新；这不会轮询 JIRA。推送恢复先取快照与游标，缺口不能靠旧缓存补成成功。

11. 文件、工作区与部署

  • PostgreSQL 和 GameCLIServer 可先在同一台 Windows 机器部署。执行机只需 GameCLI、Agent 运行环境及任务工作区；不需要各自安装数据库。
  • 实施时确认 PostgreSQL 实际版本、端口和账户；应用使用独立最小权限账户，DDL 迁移使用单独权限。数据库不向执行节点直接开放。
  • 数据库连接、文件目录、端口、任务容量、心跳与租约参数由服务端配置管理；提交 .env.example，不提交实际密码、令牌或 .env。
  • 需求文件采用临时上传 → 哈希/大小检查 → 持久归档 → 数据库引用；拒绝路径穿越和非授权下载，清理无引用临时文件须有保留期。
  • 每次执行使用隔离工作区或 Git worktree；同一个可写目录不交给多个 Agent。返回代码提交哈希和资源哈希，不只返回本机绝对路径。
  • 后台 GameCLI 与聊天、看板独立生命周期；服务退出停止新派工并保存未决发送，执行端重连后核对状态。
  • 数据库备份与文件备份覆盖同一业务检查点，定期演练恢复；迁移失败阻止服务以不兼容结构继续写入。
  • 本期只实现启动联调和证据提交；未真实开发或验收的任务，界面标明模拟/联调，不能写成生产完成。

12.1 必须覆盖的验证

  • 审批：相同版本重复点击、旧页面提交、新修订产生、无审批权限及 Agent 冒充用户。
  • 计划：交付标准遗漏、跨项目引用、环形依赖、重复子任务及计划发布中断。
  • 并发：同任务双领取、节点容量超额、重复消息、确认丢失、结果重复。
  • 恢复：节点失联、服务重启、数据库中断、取消无响应、旧代次迟到、文件上传中断。
  • 界面：约 400～480 像素侧栏、普通宽屏、键盘导航、空数据、长文档和长任务号；最终实测而非只检查代码。
  • 证据：结果评论、代码/资源版本、QA 输入一致；无证据不标记完成。

上述为待执行计划。数据库集成测试使用隔离数据库和临时文件目录；不得使用生产任务做崩溃或并发实验。

13. 迁移与后续查询入口

  1. 保留现有 JIRA 链路作为历史基线，新 PostgreSQL 路径在隔离测试项目中开发。
  2. 更新角色技能和 CLI 契约：PM 由 JIRA 建单改为提交内部任务计划；Orchestrator 以服务端状态为准；Design 的文档规则保留。
  3. 若需要历史任务迁移，先做只读导出与映射报告，经确认后导入，保留原单号、附件来源和审批证据；不把未知历史审批补成已批准。
  4. 切换前停止旧 watch/dispatch 新派工，核对全部运行执行；启用明确的存储后端/调度模式，防止旧 JIRA 和新数据库同时调度。
  5. 回退前停止新领取并核实副作用；不能简单恢复旧命令而丢弃数据库中的未结束执行。

旧文档中的 JIRA 规则仅适用于旧实现；新开发以本文为入口，相关 SKILL 在业务迁移时同步，不能把更新指导文档误当作代码迁移完成。
