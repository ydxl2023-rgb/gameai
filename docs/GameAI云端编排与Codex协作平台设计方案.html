1. 设计目标与决策摘要

将单机 GameCLI 扩展为团队协作平台：人在 Codex 中讨论需求，在扩展 UI 中人工审阅和审批，多个执行节点承担五种专业角色，GameCLIServer 编排器集中核验和派工，Track 在 Codex 的 MCP App 组件中展示团队任务。CLI 仍是业务操作与本地工具的主要入口。

方案状态：技术方向已确认，作为后续开发指导；新增能力待实现；不是已完成的功能。 本文不批准新业务需求、不启动专业制作、不迁移服务、不修改现有 JIRA。七日登录主任务 AI9527-5 的已批准需求与 16 项任务保持原样。
决策建议方案边界
编排服务扩展现有 GameCLIServer，使用 Node.js + TypeScript；首版单实例、单写入者允许多台执行机；暂不做多活调度。现有 C# CLI 保留，不再新建 Python 编排服务。
通信GameCLI 使用 WebSocket 实时调度与 HTTP 业务接口；看板使用 MCP 工具桥接本期采用 WebSocket 常驻连接；HTTP 长轮询不列入首版必做项。
角色Design、PM、Art、Development、QA 各自可有多个执行实例角色不是机器；一个节点可声明多种能力，每次执行只有一个负责角色。
界面独立网页组件，通过薄 MCP 服务嵌入 Codex本机存在实现，账号开关及自建组件端到端渲染尚未验证。保留网页降级。
权威状态JIRA 保存审批、依赖、执行、重试及交付引用不引入 SQLite 或第二套业务状态库；运行缓存不能批准、完成或重新派工。
执行方式本期提供后台常驻 GameCLI 自动接单；保留一次性 CLI 用于提交、查询和配置MCP 通知、网页显示和 CLI 返回都不能自动唤醒已结束的对话。

3.1 更新方式

首版 MCP 组件通过宿主桥接调用只读快照／增量工具，建议可见时每 3 秒刷新一次；请求的是编排器运行缓存，不逐次读取 JIRA，也不需要每次唤起模型。宿主桥接是否允许定时调用纳入能力验证。不支持时采用手动刷新和独立网页。可选网页通过 HTTP SSE 接收序号事件，断线用游标恢复，存在缺口先重取快照。MCP 内直连 SSE 只有在认证、连接来源许可和宿主实测通过后启用，不作为首版前提。

3.2 界面表现交付

桌面工具使用简洁列表、状态标记和通用图标；无游戏美术资源、特效或按钮音效需求，不新增打开／关闭动画。列表、错误态、详情和日志为可访问网页组件；持久化筛选与分隔比例属于偏好，不是业务状态。

4. 职责、实例与执行模式

对象职责不得承担
Design参考成熟产品形成草案，一次集中澄清，修订后提交完整审阅版自行批准需求、直接指挥其他专业。
PM以交付标准拆分任务、维护覆盖清单、依赖及变更影响每专业一张大包、并发改写同一主任务的已发布计划。
Art资源制作、导入规范、预览与交付证据用文字说明冒充真实资源，代替人工抽检。
Development按明确任务编码、集成、自测及提交可复现版本修改未批准规则或绕过上游产物门禁。
QA专项和集成验收，按证据分类缺陷、提交回归结果把未执行写成通过，代替开发直接修改业务实现。
Orchestrator确定性状态机、资格筛选、任务占用、校验、失败恢复作为另一个大模型自由决定审批或任务完成。

节点标识一台受控执行环境；Agent 实例标识某个专业会话；执行编号标识一次任务尝试。三者不能共用一个 ID。节点注册声明 project、roles、工具能力、Unity 版本、平台、并发容量及工作区能力。

模式启动者生命周期
对话执行当前 Codex 通过 CLI 原子领取任务当前对话完成专业工作；本地监护进程续租，检测宿主失联后停止续租并请求核对，不无限续租。
后台执行用户明确启用 GameCLI worker run常驻进程通过 WebSocket 接收任务分配，启动独立 Codex 会话、采集日志、处理取消和上传。对话结束不影响该受托管进程。
观察模式用户打开 Track 或 Unity 面板只读，不领取、不续租、不通过观察行为启动专业代理。

本期后台模式默认每节点同时执行 1 项；有隔离工作区及足够资源后按角色提高容量。多个 PM 可处理不同需求；同一需求的版本编辑、批准、计划发布均由服务串行处理。一个 QA 节点可并行处理日志审阅，但启动 Unity 的槽位独立限流。

4.1 GameCLI 后台生命周期（本期必需）

一个常驻 GameCLI 主进程负责注册、WebSocket 连接与重连、心跳、续租、取消、Agent 启动和结果回传。每项任务使用独立专业会话及隔离工作区，结束后释放容量，主进程继续等待；不是每个任务都重启 GameCLI。

查询、提交和配置保留一次性命令，执行后退出。后台入口建议 GameCLI worker run --role pm --max-concurrency 1（待实现）。开发期可前台查看日志，后台部署由进程管理器托管并隐藏窗口；开机启动和故障恢复要实际实现。

心跳、续租和取消独立于 Agent 执行与文件上传，不能被耗时操作阻塞。关闭 Track 或结束 Codex 对话不停止已授权后台任务。“暂停接单”不终止当前任务；“停止节点”先暂停再处理当前执行，取消结果未知不能直接释放并重派。

5. 从需求到交付的完整链路

Codex 讨论需求 → Design 草案与集中澄清
↓
扩展 UI 展示完整需求 → 人工批准此版本并启动流程
↓ 云端保存 JIRA 审批，上传并核验附件
云端选择空闲 PM GameCLI → 内部 PM Agent 拆分建单
↓ GameCLI 回报结果；云编排器重新核验 JIRA
云端选择依赖就绪任务和空闲专业 GameCLI
↓
后台 GameCLI 启动 Agent → 回传状态和结果 → Track 展示

本期只验收审批、派工、Agent 启动和回传闭环。下述真实制作、Unity 验证及完整 QA 属于后续生产流程；联调不能把未验证的生产任务标记为完成。

  • 用户在 Codex 输入文字或文件；CLI 向中央服务登记需求，服务生成主任务或复用已有主任务。需求入口不是 Unity 手填面板。
  • Design 执行：先提供真实参考来源；形成推荐草案，所有重要决策一次集中展示。研究工具不可用时由对话宿主提供可核验来源，不伪称已调研。
  • 用户一次反馈后统一修订；最终 HTML 含线框、交互闭环、配置字段与验收标准。Design 文档保存于目标仓库根相对路径 app/desgin/，不存在自动创建。
  • 扩展 UI 展示完整需求、线框、配置和交付标准；用户点击“批准此版本并启动流程”。服务校验 expected_revision 和文档哈希，写入 JIRA 中的批准者、时间及启动授权后才显示已批准。重复点击复用回执，旧页面版本过期则拒绝批准。业务规则变化必须重新审阅。
  • 先上传主任务附件并远端核验；总共最多 3 次上传尝试，响应未知先查附件，失败或无法核验时不启动 PM。
  • 云编排器选择空闲且具备 PM 能力的后台 GameCLI，由其启动内部 PM Agent 形成按交付标准拆分的完整计划；每个标准映射实现和验收任务。服务校验 ID、角色、依赖无环、拓扑顺序、范围覆盖与现有任务映射；语义覆盖还需审阅，不能声称只靠字段校验可证明完整。
  • 服务先保存计划及建单意图，授权该 GameCLI 的确定性适配代码创建或复用子任务。GameCLI 回报执行编号、真实单号及计划版本；云端重新读取 JIRA 核验父子关系、依赖、需求版本和附件。全部发布后才开放专业任务领取；同一主任务只允许一个发布执行者。
  • UI 的“批准此版本并启动流程”已包含后续自动派工授权，不需要建单后再次下令。后台执行端等待就绪任务；服务读取 JIRA 审批、计划、上游交付与状态，选择能力匹配且有空闲容量的节点，登记执行与租约后返回任务包。
  • Art 上传真实资源及证据，校验后进入待抽检；人工确认实际交付版本后才放行其下游。无美术依赖的程序任务无需等待无关资源。
  • Development 在独立工作区实现，运行确定性 Unity 检查，提交代码版本、产物清单及报告；通过交付门禁后进入对应 QA，不增设额外程序人工审批。
  • QA 按固定版本验证；代码问题交程序，美术问题交美术，需求问题交 Design 重新审批，环境问题进入阻塞。修复由编排器调度，同一任务累计最多 3 次执行尝试；网络投递重试与专业重跑分别计数。
  • 所有必要制作与专项验收完成后执行集成验收；用户完成最终验收。Git 合并／发布是独立人工关口，不能把需求批准解释为发布授权。
  • 每次执行成功、失败、阻塞或取消都由服务以执行编号去重写入 JIRA 中文评论，并记录产物与真实验证结果。服务评论写入引发的通知只能重新核对，不能循环派工。

6. 状态归属与跨机器一致性

数据权威位置缓存规则
需求、批准、计划、依赖、任务状态JIRA 字段／版本化属性界面可缓存展示；派工、提交、审批前必须核对最新值。
执行编号、租约代次、占用、重试、副作用意图、交付回执JIRA 版本化属性首版仅单调度实例写入；JIRA 不提供跨系统事务或通用原子比较交换保证。
节点连接、即时心跳、CPU、最近日志、统计视图服务内存，可丢弃重建丢失后显示未知；不能据此认定任务未执行、已完成或可重新派工。
代码及集成版本Git 不可变 commit；引用写入 JIRA工作树为本地执行空间，不作为跨机器交付位置。
文档、资源、报告、完整日志共享产物存储；地址、哈希及版本登记 JIRA下载时校验哈希；以不可变执行目录保存，不覆盖旧版本。
角色及工具能力配置服务受控配置与节点本地配置不允许客户端自报角色就获得任意项目权限；本地绝对路径不向其他节点广播。

6.1 首版一致性策略

云编排器唯一维护审批、计划、租约和推进状态。PM GameCLI 只执行当前有效租约授权的建单操作；可通过云端受控建单接口操作 JIRA，凭据仍仅保存在服务器。GameCLI 不直接覆盖云端工作流属性。完成通知仅触发核验，不是完成凭证。

在一个服务进程内按主任务及子任务使用串行执行区，保证两个同时 claim 请求只获得一个有效执行。严格只部署一个活动调度器，不开多个 Node.js 应用进程共同派工；可增加只读入口但不增加写入者。重启后先从 JIRA 恢复所有开放执行，核对旧工作进程和副作用，再恢复领取。

当前不引入独立业务数据库。若以后要求多实例高可用，应另立设计，增加可靠的原子协调与 fencing，并明确协调数据不替代 JIRA 业务事实；不能直接把服务复制两份，也不能以 JIRA 先读后写冒充分布式锁。

6.2 版本与体积

需求版本、附件哈希、计划版本、任务范围哈希、执行代次、上游交付版本及 Git 基线共同约束提交。现有 gzip-base64-v1 大快照、32000 字节属性限制、1MB 解压上限保持兼容。跨节点前为 TypeScript/Node.js 与 C# 建立黄金样本，保证序列化、哈希、压缩及缺省值一致；不能各算各的需求版本。更大计划后续按任务分属性并用主清单发布版本，不能截断旧历史。当前 20 项上限维持，超限时先报告限制，不把任务重新合并成大包。

7. 领取、租约、异常与恢复

任务业务状态与执行状态分离：任务可以“待开发”但执行已领取；节点“在线”不等于任务进度正常。执行建议状态：领取登记中 → 已领取 → 执行中 → 结果核验中 → 已交付／失败／阻塞；另设取消中、结果待核实、租约失联待核实。

  • 领取请求携带 request_id 和可重复使用的 idempotency_key。服务登记 JIRA 执行意图后返回 execution_id、lease_id、generation 及到期时间。写入结果不明时先核对，不能把第二次领取视为新执行。
  • 建议节点每 15 秒心跳，45 秒无心跳显示失联；租约有效期 180 秒，续租写入 JIRA 建议每 60 秒一次。这些是待压测的初值。心跳只更新运行视图，租约续期由代码处理，不依赖大模型。
  • 心跳消失或租约到期只进入待核实，不立即把任务转派；必须核对旧进程、上传、Git 版本和其他远端副作用。若无法证明停止，保留阻塞并告警。
  • 决定重新派工时提高 generation；所有续租和提交必须匹配当前代次。旧执行只能作为迟到证据保留，不得覆盖当前结果。产物写入执行专属目录，禁止覆盖共享可变路径。
  • 提交采用不可变产物与结果摘要；服务重新验证输入版本和前置状态，成功登记回执后才返回已提交。响应丢失时按 execution_id 查询回执，不能再跑 Agent。
  • JIRA 不可用时不领取、不批准、不完成；既有执行可保留局部工作，但不能正式发布。租约将过期时本地监护请求停止，无法确认停止则保持未知。
  • 取消分两步：服务记录取消意图，执行端停止目标进程并提交证据。不能因界面点击取消立即释放工作区或重派。
  • 每次真正专业重跑有新的执行编号并计数；超过 3 次进入人工处理。模型提出重试建议不等于服务允许重试。权限失败、需求冲突、用户拒绝和未知副作用禁止盲目自动重跑。
  • 对旧计划 replan 保持现有边界：只迁移未开始、无交付记录的计划，保留旧计划及编号映射。已经执行的任务走变更流程，不能重置状态掩盖历史。

8.2 界面层最小工具

MCP 提供 track_open、track_snapshot、track_execution、track_logs、requirement_review，以及人工交互专用的 requirement_approve_and_start；另提供受控的暂停接单和取消请求。审批不能由模型或页面自动调用代替人工确认。track_open 关联 text/html;profile=mcp-app 界面资源，其他工具返回结构化数据。是否允许组件直接调用工具由宿主能力与权限决定；界面不获得任意 shell、JIRA Token 或任意文件读写权限。

CLI 通信、Agent 生命周期、本地检查和产物打包仍由 C# 执行。Unity CLI 留待后续，本期不接入、不调用。远程 MCP 不能直接运行用户电脑上的 CLI；需要本地工作时由 Codex 调用 CLI 或已注册执行端处理。远程身份由服务验证，不能信任组件提交的 approver 名称。返回 202 仅表示受理；CLI 区分已完成、受理中、阻塞、执行失败和结果未知。

8.3 实时调度与业务接口分工

8.4 接单确认与断线恢复

  1. 云端先在 JIRA 持久化分配记录与执行租约，再向指定节点发送任务；消息发送成功不等于接单成功。
  2. 派发消息携带协议版本、消息编号、任务编号、执行编号、租约代次与到期时间。GameCLI 确认接单并核验有效租约后才启动 Agent；重复消息返回同一确认，不重复启动。
  3. 断线后采用有上限且带随机抖动的重连退避；恢复时上报节点身份、未结束执行及最后确认信息，核对权威状态后再恢复调度，不能只依赖内存消息重放。
  4. 心跳在线不等于业务租约有效，续租必须收到服务端持久化确认。失联或租约过期进入待核实状态；旧执行和副作用未核清前不得立即转派。拒绝旧代次的续租及结果。
  5. 最终结果通过 HTTP 携带执行编号、租约代次和幂等键提交。响应丢失先查回执，重复提交不得重复写评论或推进后续任务；只有持久化并核验成功才推进。
  6. 生产部署使用安全连接和节点身份校验，配置代理连接升级、空闲超时、心跳、消息大小上限和有界发送队列。进度可合并，任务与取消指令必须确认，不得静默丢弃。

50 人团队不以人数直接判断协议容量：需实测活跃节点数、消息频率、日志量和重连峰值。两种传输都不能解决业务幂等或自动降低 JIRA 写入量；JIRA 通知与核验集中在服务端完成。

8.5 通知与负载

JIRA Webhook 是变化提示，服务收到后集中合并同一任务事件并读取最新状态。WebSocket 状态同步和看板刷新使用中央缓存／队列；任务派发及状态推进仍须核验并持久化到 JIRA，不导致每客户端轮询 JIRA。丢失通知无法靠传输本身完全解决：启动、重连、缺口后集中重新核对；静默漏通知可配置低频单中心补偿扫描，或明确接受仅人工补偿，不声称零轮询就保证零丢失。JIRA 请求设置统一并发上限、退避及限流处理。

9. 工作区、资产与后续 Unity 验证

Unity CLI 本期不工作：不安装、不调用、不作为节点接单或任务启动前置条件。下述 Unity 要求仅用于后续正式制作阶段；缺少真实验证的结果标为“尚未验证”，不能自动通过生产验收。

9.1 独立工作区与集成

  • 每个代码执行使用独立 Git worktree，分支建议 codex/任务号-执行短编号，保留用户已有改动。禁止多个程序 Agent 共写同一 Unity 项目目录。
  • 上游代码作为不可变 commit 提供；下游不能读取另一台机器的未提交工作树。PM 计划明确模块接口与实际代码依赖，执行端根据任务包准备集成基线。
  • 同一目标分支的候选集成串行处理；冲突进入明确集成修复任务，重新跑验证。候选集成分支不是向主分支发布，正式合并仍走人工关口。
  • 美术保存实际资源、预览、导入参数及可用时的生成模型／种子信息；不支持种子的工具如实注明。Unity 资产保持 .meta GUID，不在多节点重复生成不一致标识。
  • 产物存储可先使用受控文件服务，后续迁移对象存储；JIRA 仅保存地址、大小、哈希和版本。上传完成不等于交付通过，下载方重新验哈希。

9.2 确定性验证契约

固定 Unity 精确版本、依赖锁文件、代码 commit、资产哈希、测试输入及随机种子；报告记录环境、命令、退出码、测试明细、日志与截图。确定性指同输入和环境得到可复核结论，不承诺所有二进制逐字节一致。根据平台与许可证选择真实可用执行机，不假定 Unity GUI 测试都能在容器中完成。

QA 只能针对明确的构建或集成 commit 验收；上游变更后旧结论失效。工具缺失、许可证不足、运行环境不可用进入阻塞；禁止用桩报告冒充真实测试。

10.1 技术栈与实施约束

  • 服务端采用 Node.js 运行时，新增编排模块使用 TypeScript。现有 JavaScript 在保持协议兼容及测试通过的前提下逐步迁移，不因更换语言一次重写服务。
  • 内部划分 JIRA 接入、需求审批、节点管理、任务调度、执行管理、结果处理与看板接口。HTTP、WebSocket、MCP 复用同一应用用例，不能分别维护状态机。
  • TypeScript 启用严格类型检查；网络消息、配置与 JIRA 返回值仍需运行时校验。C# 和 TypeScript 的版本、哈希、压缩和幂等契约使用共同测试样本验证。
  • 提供构建、启动与测试脚本，由 Node.js 运行编译产物；构建输出和依赖缓存不提交，依赖锁文件提交。实施时固定受支持的运行时及依赖版本。
  • 主事件循环不得执行长时间同步计算或阻塞 I/O；消息与日志队列有界。耗时计算交给独立工作进程或执行节点，避免阻塞心跳、续租和取消。
  • 服务器负责决定谁在何时执行哪个任务；C#/.NET GameCLI 负责本地工作区、专业 Agent 启动与结果回传。本期不接入 Unity CLI。
  • 未来确需 Python 专用计算库时可按需调用独立工具，不引入第二套编排器或业务状态源。
  • 保留现有服务名称与部署入口，升级时验证 Webhook 和消息兼容；接管项目时停止旧客户端自动派工，只保留一个活动调度写入者。

10.2 部署与信任边界

服务器可先放局域网，Node.js 由进程管理器托管，浏览器 UI 静态文件与 API 同源部署。开发验证不自动重新启用旧服务中已删除的认证。本方案的跨机派工和远程取消具有新的写入权限，应设计可识别用户、节点和项目的身份机制；公网部署启用 TLS 及可撤销凭据。若继续采用免认证内网模式，应限制为受控试验环境，不宣称具备用户隔离。

JIRA 凭据只存服务端受控凭据配置；日志隐藏 Token、签名下载地址和敏感输入。备份 JIRA 与产物存储；节点只保存可重建工作区和临时上传缓冲。服务恢复以 JIRA 为准，不靠本地缓存跳过审批。

后续阶段 5：生产级缺陷与发布闭环在本期后台执行端基础上扩展真实验证、缺陷回流与发布对话结束仍执行已授权任务，离线不盲目转派，修复次数和最终审批正确。

11.1 切换与回退

  1. 停止旧 watch/dispatch，等待或核对全部运行执行；备份当前 JIRA 属性、技能版本和产物引用。
  2. 先以只读模式比对 TypeScript/Node.js 与 C# 对同一任务的版本、依赖和门禁结论。
  3. 指定项目由中央服务接管写入，节点升级到拒绝旧调度的版本，再开放领取。
  4. 回退先停止新领取，确认已运行执行及远端副作用，完整同步 JIRA 回执后再交回旧单机；不能直接让旧 CLI 解读不兼容的新属性。

七日登录现有任务可用作只读兼容样本；并发、崩溃和重试实验使用隔离测试任务，不以重跑生产美术／程序来验证协议。
