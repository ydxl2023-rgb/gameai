1. 目标与范围

让已批准需求的任务拆分可追溯、可验证、可重放。本文记录未来改造计划，不表示这些能力已经实现，也不授权执行现有需求。

当前采用单 PM RodFergusson，内部 UI、Art 模块共同规划；Program 暂不启用。先验证一个独立窗口的白模、图片资源包、最终装配三项交付。

确定性目标：同一份批准清单、已保存的 Agent 输出，在同版本处理规则下得到同一份规范化计划。重新调用模型属于新尝试，不保证推理结果相同。

3. 第一阶段：固定任务骨架

实施更新：已接入批准清单解析、固定骨架、PM 内容补全、事务发布前复核及逻辑编号映射。结构校验不能证明自然语言与线框的所有语义一致，仍需 Design/PM 审查。无清单旧文档需修订后重新审批。

  1. 读取批准 HTML 中唯一的 ui-delivery-manifest，校验严格 JSON、版本、范围和必填项。
  2. 检查独立窗口、内部区域归属、控件和资源编号、HTML 锚点、资源映射，以及阶段依赖。
  3. 按独立窗口生成固定骨架，内部控件不增加任务。每窗口对应白模、图片资源包、最终装配三项。
  4. 向 RodFergusson 提供固定骨架与完整窗口上下文，仅允许补充任务说明、交付内容和验收标准。
  5. 对模型输出与骨架进行逐项对照，编排器复核后才原子建单。

窗口编号、角色、交付阶段、来源锚点及依赖不可由模型改动。缺少清单、清单与正文冲突或存在未决边界时必须停止，不按线框张数猜测，不静默修补已批准文档。

骨架使用稳定逻辑编号；数据库公开任务编号由发布时分配，两者保存映射。当前不生成程序或 QA 任务。无新增图片时按批准清单交付资源核对与映射，不虚构生图。

验收：一个窗口得到三项，两个窗口得到六项；控件增加不增加任务；新增、漏项、重复、改角色、改依赖、失效锚点均被拒绝；无效计划不产生任何任务。

4. 第二阶段：执行快照与离线重放

统一执行包记录批准文档、清单、实际技能、提示词、Agent 原始输出、规范化结果与校验报告。保存执行编号、尝试编号、输入哈希、CLI 与校验器版本、schema 版本、可获取的模型配置、时间和工具结果；不可获取的信息明确缺失，不伪造。

  manifest.json
  requirement.html
  skills/
  prompt.txt
  skeleton.json
  agent-output.json
  plan.json
  validation.json

以上目录是工作区示意。需要长期重放的完整执行包必须另行保存至有保留策略的正式产物存储，不能只依赖会被清理的 temp；平台记录其位置和哈希。

先固化输入，后执行；真正传入模型的技能必须来自该快照。原始输出不可覆盖，规范化结果单独保存。记录不得包含令牌、密码或数据库凭据。

离线重放读取执行包，以指定版本规则重新生成骨架并验证保存的输出，不调用模型、不建单、不改审批状态。规范化明确对象键序、任务与依赖排序、UTF-8 编码等哈希规则，不擅自改变描述正文语义。

验收：相同包重复重放产生相同计划哈希；源文件或技能被修改不影响旧包；篡改内容可检测；缺少依赖版本明确失败；不支持的 schema 不静默按新版解释。

5. 第三阶段：重试与发布一致性

  • 传输或发布失败：重新提交保存的同一计划，不重新调用模型。
  • 需要重新推理：创建新尝试，保留旧输入输出和失败原因。
  • 相同发布请求与相同计划哈希：返回原发布结果及任务编号映射。
  • 相同请求但内容哈希不同：明确拒绝。
  • 发布前再次核对当前批准版本、权限及任务计划；旧版本失效则停止。
  • 所有任务通过才在一个事务内创建；超时、并发或服务恢复时先查询既有结果，不盲目重建。

验收：重复提交、并发提交、响应丢失后的重试均只产生一套任务；部分写入失败全部回滚；旧版本不能覆盖新审批；新尝试与原尝试可分别追踪。

6. 职责与实施顺序

部分职责
策划提供人类可读内容与一致的机器清单，提前解决窗口边界
RodFergusson补充固定骨架的说明与验收内容，报告缺口，不控制发布
GameCLI固化输入、调用模型、保存原始结果、执行本地预检查与离线重放
云编排器权威审批核对、骨架与结果校验、幂等发布、事务和状态管理
共享契约统一版本化 schema、规范化规则和测试样例；避免 C# 与 Node.js 规则漂移

GameCLI 不成为第二套业务编排器；模型输出不是执行授权，本地预检查不能替代服务端校验。

推荐顺序：先完成第一阶段并用一个窗口验证，再实施快照与重放，最后强化发布重试。第一阶段稳定前不扩展程序任务、多 PM 或全专业并行。后续每阶段交付都应标明实际实现、验证证据及剩余限制。
