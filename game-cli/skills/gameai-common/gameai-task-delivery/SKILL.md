# 任务依赖与交付

本技能只规定交付门禁，不定义玩法、美术风格或编码细节。平台 是依赖、审批、执行和交付版本的唯一可信来源；本地只保存实际文件与证据。

## 顺序与职责

- PM 按 [交付标准拆分规范](../../gameai-pm/SKILL.md) 建立任务级依赖图，同一专业可有多张子任务。使用美术产物的程序任务遵循“所需美术交付并抽检完成 → 对应程序交付并校验完成 → 对应测试验收 → 用户最终验收”；不使用美术的逻辑任务无需等待无关美术。最终集成验收汇合全部必要交付与专项验收，不增加程序人工审批。
- 项目管理负责建立主任务、专业子任务和 `depends_on`；编排器负责核验和启动代理。父子归属不能代替依赖。
- 需求确认前只保留需求主任务，不创建专业子任务；用户确认后由 PM 建单，执行前必须有当前版本的需求审批及已发布计划。不能把创建单据解释为批准执行。
- 每次启动由 GameCLIServer 从 PostgreSQL 读取最新平台状态，并通过固定 Agent claim 与任务输入提供已核验上下文；Agent 不直接读取凭据、数据库或尝试猜测服务端口。所有前置子任务必须属于同一需求，状态为完成，交付清单有效，实际文件存在且哈希一致，证据齐全。
- 上游重新打开、文件变化、需求修订或交付版本替换后，下游原交付失效；不能凭旧的完成状态继续放行。

## 专业交付

- 美术：符合任务范围的界面设计、布局尺寸、触屏交互说明、资源及预览、导入要求。程序先读取这些文件，再实现界面；不可用文字猜测替代美术交付。
- 程序：实际修改的代码与界面资源、构建和功能检查报告，记录所使用的美术版本。遵守工程编码规范，保留用户修改。
- 验收：对指定程序和美术版本逐项验证验收标准，给出真实日志、截图或报告。未运行、失败或证据缺失不能报告通过。
- 宿主指定结构时返回 `verdict`（`pass`、`fail`、`blocked`）、中文 `summary`、`artifacts`、`checks`。
- 每个产物包含工程相对 `path`、实际小写 `sha256`、中文 `purpose`；包含真实成果和验证报告，不得只交付一份自称完成的说明。
- 每项检查包含中文 `name`、真实 `passed`、指向本次产物的 `evidence_path`。宿主验证文件完整性；哈希正确不等于视觉、玩法或测试结论正确。
- 缺少生成工具、运行环境或无法验证时明确阻塞，不能用占位图、空文件或编造报告冒充最终交付。

## 执行与审核

- 代理只在授权的工程与任务范围内制作和验证，不能批准自己的成果、修改上游产物或自行调度其他角色。
- 提交前再次核对审批、执行身份和上游版本，防止运行期间变更被忽略。
- 每次成功、阻塞、失败或取消均由平台保存执行编号、角色、会话、版本、产物与证据，并追加中文任务评论。结果未知时先读取现有记录，不重复派工。
- 显式开启自动推进的计划中，美术和程序在宿主校验实际交付与检查证据后标记工程交付完成，供后续已勾选任务使用；这不替代美术质量抽检或最终验收。QA 通过后进入待验收，由人工最终验收。代理不能自行合并或发布。
- 重试由平台控制，默认最多三次；执行中的记录不得自动重试，先核实原进程和副作用。上游版本变化必须重新检查下游有效性。
- 当前人工派发及同计划自动推进由云服务执行。模型只返回结果，云服务复核当前批准版本、上游产物、执行身份、files 与 checks 后保存状态。输入中 platform_context.authoritative 为 true 且标明核验时间时，视为宿主完成启动前平台读取；不能因模型无法访问服务端口而重复阻塞。若上下文缺失或云端续约失效则停止。

描述遵守 [任务描述规范](../gameai-task-writing/SKILL.md)。
