# UI 模板复用的授权变更契约

## 默认与明确要求

- 既有 UI 的换皮、美化、风格迁移默认保留全部节点身份、层级、顺序、激活状态、组件、文本含义和引用。不能自动精简渠道入口、隐藏窗口或看似无用的按钮。
- 用户明确要求新增、删除、移动或更改功能时，以该指令为本次允许差异；不是永久禁止增删。明确的指令无需再次询问。仅对目标歧义、未定义交互或影响其他功能的关联变更提问。
- 删除父节点不等于可以删除外部共享依赖；列出专属子树删除和引用修复。新增入口必须明确必要子控件及交互边界。
- 不支持的脚本不迁移，但保留对应 UI 入口并记录功能缺口；不得以技术不支持为由静默删除。

## 基线、清单、执行

1. 锁定数据库模板版本和原始快照 SHA-256。v2 数据需显式导出其完整 hierarchy 为 ui-template/1，不可先精简再声称是基线；保留转换证据。
2. 将人类要求整理为节点 ID 与具体字段的变更清单。每条含 JSON pointer path、beforeExists、before、afterExists、after。节点与组件数组按 ID 比较，其余数组按完整值比较；路径使用 ~0/~1 转义。
3. 新增/删除节点记录完整对象；修改字段记录精确旧值和新值。视觉资源映射、预览输出等新增字段也须进入清单，不支持通配符授权。
4. `ui-library guard --baseline <源快照> --candidate <候选快照> --output <新audit.json>` 只输出待核对差异，不代表授权。禁止直接把全部 audit 差异自动批准；必须逐项对应用户指令。
5. 核对后的 approval 使用 ui-change-approval/1，包含 sourceSha256、outputPrefab、authorizationReference（实际用户指令来源）、changes。明确的风格要求允许执行者选择具体美术资源并登记精确映射，不要求用户逐个批准图片文件哈希。
6. 加 `--approval <清单.json>` 生成 ui-assembly/2；清单与实际差异必须完全相同，源哈希、目标路径固定。UnityCLI `prefab restore` 对封装再次比较，然后才导入贴图或写预制。先 --dry-run，再正式执行。
7. 交付对照源与最终预制的节点 ID、组件、引用与真实效果。差异一致不等于功能测试通过；Unity 仍检查类型、引用及层级，运行行为另验。

## 边界

- 哈希及 authorizationReference 是可追溯记录，不是人类身份签名。宿主须从真实对话/审批取得授权，Agent 不得自造批准。工具防止清单外改动，无法证明自由文本指令的真实性。
- 当前底层 prefab restore 的原始快照入口仍用于无基线导入，不是全局安全沙箱。已有模板换皮/改造必须走 guard 封装，禁止降级裸 JSON 或 create 绕过失败；Track 服务强制绑定授权身份尚未接入。
- 不将这项规则误用于全新 UI 制作；无既有模板时按需求创建，不虚构基线。
