# 纲要式文档输出规范

## 强制适用范围

以后 GameCLI 流程中向用户交付的文档统一采用用户提供的《全AI流程规划纲要.html》的阅读方式：独立 HTML、封面、可点击目录、编号章节、分层列表、表格与打印样式。需求草案、修订稿、最终稿、设计方案、开发说明和验收报告均适用。除非用户明确指定其他格式，不能仅交付 Markdown、纯聊天长文或原始 JSON 代替阅读文档。

这项要求限定用户阅读产物。标准技能仍使用 SKILL.md，CLI 与 Agent 仍遵守 JSON schema，任务正文仍遵守单据编写规范，不向这些接口塞入整页 HTML。短答复和进度通知无需生成文档。

PM 拆分后的专业任务单据也必须逐项输出为独立 HTML，任务目录链接到对应单据；美术及界面实现／验收单据直接嵌入对应可见线框，组件任务包含分层示意。后台逻辑单据区分关联界面上下文与实际交付范围，不用纯文字或外部引用替代必需图示。各单据保留版本、来源、依赖和交付标准，详细任务要求见 [PM 规范](../../pm/RodFergusson/SKILL.md)。

## 模板与排版

- 使用随技能分发的 [HTML 模板](assets/outline-template.html)，保留参考纲要的浅灰背景、居中白色页面、中文字体、封面、目录、标题分隔线、表格、提示框和打印按钮。模板不依赖原开发机器上的文件。
- 交付为 UTF-8 编码的单文件 HTML，样式内嵌，不依赖外部字体、脚本或网络才能阅读正文。允许保留真实参考链接。
- 封面显示中文标题、用途、日期、版本与真实状态；存在 平台 任务时附编号与链接。完整需求 revision 必须可查看，不用展示版本代替审批版本。
- 目录链接对应真实且唯一的章节锚点；正文采用 1、1.1 等连续编号，不强行照搬参考纲要的业务章节。根据文档类型组织调研依据、目标、范围、规则、界面、交付、依赖和验收等内容。
- 每条规则独立成行。比较和映射使用表格，流程可以使用内嵌图示；正文不能只展示摘要或原始结构化快照。
- 每个测试用例分为前置条件、操作步骤、预期结果，各项分行；保留尚未执行、实际通过或失败的真实标记。
- 标题与描述使用中文；字段名、代码标识符、路径、真实单据编号和链接保留必要原文。
- 窄窗口可读，长版本号与链接换行；打印时隐藏操作按钮并保留完整正文。禁止用固定高度或裁剪隐藏需求。

## 必须产出的界面线框布局图

### 窗口整体先于结构分解（硬性规范）

- 第三节3.1展示主要窗口完整效果，然后紧跟本窗口结构分解与控件属性；3.2起依交互逻辑展示弹出窗口及其他独立窗口，每节采用相同顺序。共享模板索引与详细内部结构放在窗口展示之后；配置表仍位于统一操作交付标准之前。按实际窗口数量连续编号，目录同步，不强制沿用旧3.3和3.4编号。
- 每个窗口采用透明Panel根容器 → Background窗口背景 → 标题、按钮、列表等实际组件。根容器不强制添加透明Image；背景通常铺满根容器，标明静态图或九宫格；纯色可直接用颜色，不强制产出贴图。遮罩、独立弹窗和点击捕获层明确所属父节点及绘制顺序。
- 窗口组件树直接使用唯一中文名称、稳定编号和复用模板链接，例如“档位卡（C01，第n实例）”。属性注明父节点、相对坐标、尺寸、锚点、控件类型、图片模式、触控及红字绘制顺序。背景改为父节点后，必须换算子节点坐标，不能沿用画布绝对坐标假称局部坐标。
- 所有滚动列表，包括复合组件内部奖励列表，必须展开ScrollRect → Viewport + RectMask2D → Content → 实体单元，不以列表名称省略结构。说明方向、裁剪边界、Content布局与单元模板；内容未溢出时保留结构但不产生无效滚动。本次七日登录档位横向、卡内奖励纵向，领取按钮在奖励ScrollRect外。同一次拖动锁定一个列表，横向交外层、纵向交内层，不同时驱动；点击与拖动区分且更新保留位置。
- 复用模板只定义一次，各窗口注明实例位置、状态与绑定差异；结构节点不等于生产任务。为PM提供“基础复用组件 → 复合组件 → 列表组装 → 窗口组装”的依赖依据，透明Panel、Viewport、Content通常随所属组件交付，不机械逐节点建单。
- 按钮实例必须同时标注业务名称、控件编号和复用模板，例如“B01 · 七日登录按钮 · 文本按钮（UI-BUTTON）”“B04 · 领取按钮 · 文本按钮（UI-BUTTON）”，不能只写“文本按钮”。按钮文字子节点也注明实际文案或状态文案来源；业务名称保持稳定，处理中等状态只改变显示文案。组件树、属性表与界面标注保持一致。通用按钮模板本身不绑定某个业务名称。
- 复用是共享定义和资源，不表示所有按钮、底板外观完全相同；明确通用模板与实际样式变体。绘制顺序仍用红字标注，不能因复用省略实例的叠放及触控顺序。

### 窗体组件与控件属性（硬性规范）

- 每一个完整窗体及独立浮层必须在可见线框旁的后续单列区域提供自己的组件示意与属性表，不能只给通用道具组件图。状态变体引用同一窗体结构并标明变化节点。
- 每个节点标记稳定控件编号、父节点、名称、类型、局部布局和绘制顺序；复用组件区分模板与实例。节点类型明确为容器、按钮、滚动列表、裁剪区域、文本或图片，不能全部泛称框体。按钮的背景和文字分别标记。
- 每张图片必须明确静态图（Image.Type.Simple）或九宫格（Image.Type.Sliced），标注保持比例、拉伸区域和边缘保护要求；九宫格注明Sprite.border顺序为左、下、右、上。未生产素材时只说明边缘约束、数值待资源实测，不伪造已配置Border。文本不得烘焙到可变图片中。
- 滚动列表明确横纵开关、Viewport裁剪节点、Content容器、单元模板、间距和尺寸；文本注明内容来源及溢出策略；按钮注明动作、状态与触控范围；图片和文本注明是否接收射线，区分视觉绘制与输入命中。
- 组件示意和属性表均明确从底到顶的绘制顺序，以红字显示顺序号及规则。同父节点使用明确的Sibling顺序，跨窗体明确叠放关系；父子结构和数字不能相互矛盾。排序号是设计顺序，不默认等于Canvas.sortingOrder。不得给每个控件无必要地建立独立Canvas。
- 以设计画布为基准给出坐标／尺寸或明确布局约束，注明坐标原点与安全区适配。Unity映射列可标注RectTransform、Button、ScrollRect、RectMask2D、Image、TMP_Text等代码标识符；设计表是制作依据，不声称已经生成预制件。
- 遮罩、关闭捕获层、滚动区域必须明确触控优先级，避免顶层透明图片拦截滚动或点击穿透；辅助编号、箭头及设备底框不进入运行预制件。
- 发布前核对每个可见控件都有属性，每张图片有模式，每个窗体有示意，所有编号／父节点／顺序与线框一致。规则文字红色；缺少上述内容时不得声明线框或文档完整。

### 重复框体与滚动列表（硬性规范）

- 任何界面出现多个同类框体（奖励档位、背包格、卡片、商品等），策划必须优先判断它们是否属于滚动列表，再确定布局；不得未经容量和交互分析直接画成静态排列。
- 明确条目数量、可变数量上限、单项尺寸、可用显示区域、排列方向和一屏可见数量。内容超出显示区域或需要连续浏览时，优先采用滚动列表；确实全部可见且不需滚动时说明静态布局的依据，不强制所有重复框体滚动。
- 必须明确横向、纵向或网格滚动，方向与实际使用场景和已确认需求一致。本次七日登录的档位为横向滚动列表，线框必须实际表现横向列表，不能省略或擅自替换为纵向列表、静态七格或分页。
- 在线框中绘制列表容器和裁剪边界、实际可见的档位框体、间距及未完全显示的下一项，并用辅助箭头与中文图注标明滑动方向。图注和辅助线不作为运行资源；不凭空添加翻页按钮、滚动条或业务操作。
- 同时提供单个档位组件及其分层示意，标出“列表容器 → 档位实例 → 道具框与文字等子组件”的真实层级与稳定编号；复用实例不能被误认为独立生产多份同类资源。
- 操作交付标准包含滑动后显示的内容、边界表现、点击领取与滑动的区分、状态更新时的列表位置规则；仅在实际需要时定义打开定位或自动定位。改变业务语义的决策进入集中确认，不以画图默默定案。
- 美术清单分别列出容器布局、单元资源及视图组装；程序负责滚动、裁剪、数据绑定和输入。交付前检查线框、交互文字、资源层级与PM拆解一致；正文声称可滚动而图中没有绘制滚动区域时不得声明线框完整。

### 规则红字（硬性要求）

- 文档中所有业务规则、约束、校验、状态迁移、交付及验收判定规则必须使用红色字体；包括列表、表格单元格、操作说明及线框内的规则注记，不能仅将“规则”标题标红。
- 使用统一的 `--rule-color: #b42318` 和 `.rule` 标记；嵌套强调、代码及链接仍保持红色，SVG 规则注记使用相同的 fill。屏幕、窄窗口及打印均保留规则红字。
- 标题、目录、普通解释、调研来源、示例数值和游戏界面的普通文本保持正常配色；不将整篇文档或游戏 UI 文字机械标红。规则须有明确文字含义，不能只靠颜色表达。

### 奖励道具框四层（硬性要求）

- 所有奖励道具框均按从底到顶的顺序独立划分：背景层、图标层、文本层、框体层。适用于活动奖励、领取成功列表、补发记录及其不同状态；多道具逐项使用相同结构。
- 背景层负责底色与底图；图标层负责道具图标／占位图；文本层负责名称、数量及明确的状态文字；框体层负责透明内部的边框／描边，不使用实心框体遮盖图标或文本。领取按钮属于独立交互控件，不混入道具图标或框体层。
- 每种奖励框使用稳定组件编号，各层使用对应的四个子编号（如 R01-L1 至 R01-L4）；线框必须实际画出四层，在图中用引线、层号／图例或纵向分层示意标明，不能只在正文写一句“四层”。各层可使用不同线型或辅助色，标注不进入游戏运行界面。
- SVG 用独立 `<g data-layer="background|icon|text|frame">` 表达四层，按绘制顺序排列；HTML/CSS 使用对应独立元素及显式叠放顺序。占位素材也必须分层，不将背景、图标、文字、边框合成不可拆解的单图。
- 第三节列出组件与层编号、各层内容、页面复用和状态变化；第四节美术交付逐层对应编号，注明制作／占位／不需要及复用关系，供 PM 按交付标准映射实际任务。不因四层规范强行拆成四张任务或扩充正式资源范围。
- 交付检查覆盖所有奖励框及正常、处理中、领取成功、失败背景和补发记录；保证名称数量不被边框遮挡，分层图与实际线框、资源清单一致。多个示意视图仍须纵向排列，禁止并排。

最终需求文档（包括交给用户整体确认的最终审阅稿）必须包含第三节内独立的“界面线框布局”小节，并纳入可点击目录。这是系统必须产出的内容，不是可选配图。缺失实际线框图的文档不能声明完整、定稿或提交整体确认，不能用纯文字描述、流程图、“美术后续提供”或未渲染的图形代码替代。

- 绘制本需求涉及的入口、主要页面或弹窗及必要的辅助页面，标明页面名称、区域划分、信息层级、按钮和关闭/返回入口。多个视图必须沿纵向按操作逻辑排列，不能并排，也不能遗漏关键操作界面。
- 采用移动端触屏布局，使用简洁低保真方框、文字、占位图标和必要连线，不引入鼠标、悬停、右键等交互，不将线框当作正式美术资源。
- 每张图配中文图注，说明入口、操作、反馈和跳转目标。关键状态用状态小图或与图中控件对应的状态表展示，覆盖需求实际涉及的正常、不可操作、处理中、异常与完成状态，不凭空扩展功能。
- 线框内容必须与当前需求规则、字段、奖励档数和交互范围一致。新出现且改变业务语义的选择必须回到集中决策流程，不能借绘图擅自增加业务要求或绕过版本确认。
- 使用内嵌 SVG 或 HTML/CSS 绘制真实可见的线框，嵌入单文件 HTML；离线打开和打印均可见。不依赖外部图片链接、在线渲染服务或安装插件。SVG 提供 viewBox、中文标题或说明，保证文字清晰、不重叠、不裁切。
- 线框是用于确认布局和交互的低保真方案，图注标明这一性质；尺寸、字体、色彩或占位图标不能被误读为已批准的正式视觉规范。
- 不虚构不存在的界面。纯后台需求也必须保留本章节，明确说明没有玩家界面，并图示真实存在的操作或结果查看界面；确实无任何界面时说明不适用的具体原因，不能用空白占位图冒充线框完成。

交付前逐项核对：目录可跳转、图实际渲染、主要页面覆盖、控件与业务一致、关键状态可理解、窄窗口可读、打印不截断。设计内容和审批以对应平台版本为准；阅读副本中的线框不能承载未记录的新业务规则。
## 生成与交付

由当前对话宿主将 Agent 的结构化结果排版为 HTML。独立 Agent 无文件权限时仍返回规定的结构化内容，不能声称已经生成文件。模板中的占位标记必须全部替换；动态文本需 HTML 转义，输入资料不可作为脚本执行。

Design 需求文档必须按 [Design 文档存放规范](../../design/ShigeruMiyamoto/SKILL.md) 输出到目标工程根目录的 `app/desgin/`，不存在时自动创建；保留该拼写，不再放入 `docs/`。其他工程说明仍可输出到 `docs/`。使用中文文件名。Markdown 可作为辅助维护源，但用户收到的主链接必须是 HTML 阅读版。生成后检查标题、目录锚点、完整内容、版本与审批状态、测试用例数量及占位符，并打开预览检查排版。

平台仍是流程与审批唯一可信来源，HTML 是对应版本的阅读副本。格式转换不能改变业务要求、重新分析需求、批准版本或创建任务。当前对话给出简短摘要及 HTML 链接，不要求用户从聊天记录拼接完整文档。

## 需求文档四节结构与交互闭环

需求文档正文固定为四节，优先简短且可验收，不重复堆叠规则、开发清单和测试说明：

1. 设计目标：用简短段落说明玩家价值、目标和本期范围。
2. 功能综述：集中说明资格、期限、核心玩法、奖励及跨页面共用规则。
3. 界面与交互：先给实际线框图，为页面与控件编号，再描述每个按钮和信息区域。按玩家操作组织交付标准；静态元素使用“编号—显示内容—更新条件”表，不机械重复验收段落。
4. 美术与表现需求：按页面或交互列出界面、图标、特效、动画、按钮音效，注明用途、触发条件和本期交付状态（制作／占位／本期不需要）。这些类别必须逐项说明，不因有栏目就默认扩大资源制作范围。

调研来源、详细测试和技术说明放附录，可使用默认收起但打印展开的区域。正文必须保留核心规则与异常处理，不能为简短而遗漏要求。

每项玩家操作必须覆盖以下六项：
- 前置条件。
- 操作步骤与处理中反馈：触发入口、请求期间显示、能否重复操作。
- 成功结果与界面反馈：业务变化、弹窗或提示内容、后续按钮、相关状态更新。
- 失败原因与界面反馈：明确业务失败的原因、提示、可执行的下一步。
- 异常恢复处理：断线、超时、响应未知时的提示，权威状态查询、重试与防重复要求。响应未知不得直接视为业务失败。
- 测试用例：列出正常、失败及异常分支的可判定测试场景；完整用例仍按前置条件、操作步骤、预期结果分行，可移至附录引用，避免正文重复。

仅写“点击按钮”或“操作成功”不构成完整交互描述。无异步请求的关闭、返回操作说明本地导航结果；存在关闭动画时必须说明动画与实际关闭的先后关系，不得一律写为即时关闭，失败和网络处理可明确不适用及原因，不能虚构网络调用。线框必须覆盖需求实际采用的处理中、成功弹窗、失败提示及恢复操作，并与控件编号对应。成功反馈是否需要特效、动画和音效必须在第四节明确，不自行默认正式资源制作。

## 打开与关闭动画的硬性要求

凡需求包含界面打开或关闭动画，第三节对应操作的“操作步骤与处理中反馈”必须明确写出动画，不能只在第四节资源清单列出，也不能仅写“打开界面”或“关闭界面”。

- 打开操作：说明点击哪个入口、何时显示界面并播放哪个打开动画、动画与数据加载的先后或并行关系、播放期间允许哪些操作、何时进入可交互状态。
- 关闭操作：说明点击关闭／返回／确定后的关闭动画、播放期间是否允许重复操作，以及动画结束后何时隐藏当前界面或返回目标页面。不得在播放动画前就销毁需要展示动画的界面。
- 对涉及动画的操作，测试场景必须覆盖动画触发、播放期间的重复点击及结束后的正确界面状态；实际支持播放中关闭或切换时，补充对应中断行为。
- 操作中的动画名称或编号与第四节“美术与表现需求”一一对应，说明用途和触发条件。交互章节不得引用未列入交付范围的动画，资源章节也不能替代操作过程描述。
- 不需要动画时，操作步骤只描述真实的界面显示、隐藏及状态变化，不添加动画句子或“无动画”占位说明，不为满足模板自行新增动画。第四节仍按范围规则标明动画类别本期不需要。

交付检查必须逐项核对打开、关闭、返回和确定操作：存在动画却未写入操作过程，或操作过程与动画交付清单不一致，均视为文档不完整，修正后才能提交整体确认。

## 线框顺序排版的硬性要求

- 线框视图一律单列纵向排列，宽屏、窄屏和打印均禁止并排、双列网格和横向轮播。
- 按玩家操作逻辑排序：入口 → 主页面 → 操作处理与成功／失败反馈 → 辅助功能分支。图前标明页面、触发控件和返回目标。
- 独立分支注明从哪个页面进入，不能画成必须依次经历的操作。成功与失败标明互斥结果，不同时出现。
- 单一界面内部可保留真实的横向按钮或奖励卡布局；本规则禁止多个线框视图并排，不改变产品界面本身。
- 交付前检查文档顺序以及响应式和打印样式，模板与产出均须符合单列规则。

## 手机底框与设计画布

本项目后续手机线框统一使用1920×1080横屏设计画布，以带刘海的 iPhone 外观作为设备背景：左侧刘海、圆角屏幕、底部手势条，标示布局安全区域。所有界面在同一比例的屏幕内部展示，继续单列按操作逻辑排序。

该尺寸是用户指定的设计画布，不宣称它是某款手机的原生分辨率。安全区域仅作示意，运行时按设备实际安全区适配。文字、按钮及关键内容避开刘海和手势区域，不裁剪或遗漏控件。设备底框和辅助标记不属于实际游戏美术交付。

优先使用内嵌 SVG 的 viewBox 保持画布比例、清晰缩放与离线打印；标注画布尺寸。不得拉伸屏幕、改变比例或把多台手机并排排列。单个屏幕内的奖励卡等可按实际横屏布局排列。

绘图时使用随技能分发的 [横屏手机底框](assets/phone-landscape-frame.svg)，在内部1920×1080画布中替换示例内容。

## 配置表设计的必备内容

涉及可配置数据的功能，第三节必须在“操作交付标准”之前提供“Excel 配置表设计”小节，并纳入目录；相应后续编号顺延。说明工作簿名、工作表职责、每行含义、字段名、类型、必填性、主键／外键、单位或范围、示例值、完整性校验和错误处理。

区分固定业务规则、策划可配置数据与玩家运行数据，不把账号进度或审批状态写入配置表。说明配置加载和生效时机、已有账号快照或兼容策略，并给出可执行的最小示例及配置测试要点。不擅自增加业务可配范围，不将示例资源路径描述为真实存在。字段设计不等于已经生成工作簿或实现导入代码；如需实际工作簿另按用户授权产出。

### 配置字段的 C# 类型

字段类型必须使用标准 C# 类型表示，例如 `string`、`int`、`long`、`float`、`double`、`decimal`、`bool`，日期等使用明确的 .NET 类型如 `DateTimeOffset`，不得使用“文本”“整数”“数字”等泛称代替类型。集合明确元素类型，如 `int[]`；可空类型明确标注，如 `int?`。根据实际语义选型，不为统一而改变原有数值范围。必填性、默认值、单位、范围和 Excel 单元格的填写／解析格式单独说明，不能混同为字段类型。字符串非空约束仍需独立校验。

### 奖励引用必须使用列表

奖励引用字段默认且必须使用一个列表字段（例如 `Rewards`），一条配置即可承载一次发放的多个奖励。即使只有一种奖励也使用单元素列表，不退化为单个道具字段，不用同档多行或 Reward1/Reward2 等列替代奖励列表。奖励档位一行一条，列表顺序即展示顺序。

配置类型栏的命名元组采用用户约定的 `List<(int:ItemId,int:Number)>` 形式；这是配置类型标记，不是可直接编译的 C# 语法。对应代码类型为 `List<(int ItemId, int Number)>`。填表使用外层列表大括号、内层条目大括号，元素顺序与类型声明严格一致。声明字段数与每项实际值数量必须相同；不推断未定义的第三项含义。字段数量、顺序或含义有矛盾时先集中澄清再定稿。

校验整份奖励列表的语法、元组长度、各项类型、道具引用及正数数量后才能发放；同一次奖励请求使用统一幂等约束，不能重试时重复发放已成功的条目。领取成功窗口和补发记录展示实际奖励列表。文档须区分配置语法、Excel 单元格写法与生成后的 C# 类型。

用户已确认奖励元组固定为两项：`ItemId`、`Number`，均为 `int`。固定配置类型为 `List<(int:ItemId,int:Number)>`，C# 类型为 `List<(int ItemId, int Number)>`。标准填表示例 `{{40,8},{10,6}}` 表示道具40发8个、道具10发6个；单项也使用 `{{40,8}}`。不允许第三项或自行引入奖励类型。奖励字典的道具主键也必须是 `int`，数量为正整数。每档一行，一个 `Rewards` 列表保存本次全部奖励，列表顺序作为展示顺序。

### 非视觉验收报告的例外

用户明确不要求截图或视觉验证、且测试对象为无图形界面的控制台程序时，HTML 报告只检查内容完整和证据一致，不强制打开浏览器或截图。不能把报告预览工具不可用升级为被测程序的验收阻塞。此例外不取消游戏界面或明确指定的视觉验收要求。


## UI 交付清单契约（硬性要求）

本节明确窗口边界，优先于按线框、组件数量推测任务的旧描述。适用于含 UI 的正式需求 HTML；文本初稿无需线框或 JSON，但独立窗口边界必须在批准前确认。

### 可见窗口清单与完整章节

第三节开头、3.1整体效果之前先列“窗口与内部区域清单”：编号、名称、是否独立交付、所属窗口、章节锚点。独立窗口使用稳定 W 编号；内部区域与控件使用稳定局部编号并注明所属窗口。独立窗口的所属窗口为空；内部区域必须指向已声明窗口。弹窗、提示条、下拉展开层、加载状态不能仅凭外观自动认定独立窗口，按明确批准的边界列入清单。边界未定须返回初稿集中澄清，不擅自增加独立交付。

每个独立窗口拥有唯一 section 锚点（如 window-W01）；章节依次包含整体线框、完整结构树、控件属性、资源映射、三阶段交付标准。3.1.1窗口说明与3.1.2控件说明等子节属于同一窗口，不拆开提取。线框、树、属性表、资源清单、JSON 使用同一组编号；修订保留已有编号，不按显示顺序重新编号。嵌套列表仍完整标注 ScrollRect/Viewport/Content/实体单元，但不因此增加交付任务。

### 资源到控件的映射

每个窗口列出资源编号、用途、目标控件完整路径、是否生成、资源类型、尺寸、透明要求、九宫格边距/切片约定与导入要求。类型明确为静态图、九宫格、文本、容器等，不把透明根 Panel、TMP 文本、裁剪容器自动列为生图资源。复用资源使用同一资源编号，并列出所有目标控件和唯一生产归属窗口，禁止重复生产。使用既有资源时给出真实引用；示例路径明确为示例，不伪造现有资产。

当前 UI 调试每个独立窗口固定三阶段：whitebox（Prefab）、art（Art）、assembly（Prefab）。资源包依赖白模，装配依赖白模与资源包。普通按钮、背景、列表项、状态归窗口内部清单，不另建任务。白模交付布局、属性与槽位；Art 交付实际需要生成的图片及映射（无新增图片须明确写明，不能虚构生图）；装配交付替换完成的预制及检查结果。每阶段明确前置、操作、成功、失败、恢复和检查方法。需要偏离此粒度时先批准例外并同步清单，PM 不自行决定。

### 机器可读清单

正式 HTML 必须内嵌且仅有一份 `<script type="application/json" id="ui-delivery-manifest">`，内容为严格 JSON，不能放在可执行脚本或只展示为代码块。清单是需求数据，不授予审批、执行或文件访问权限。保持宿主外层输出 schema 不变，JSON 放在 html 字段内部。

清单固定字段：新文档 schema_version=2（增加下述英文命名字段，旧 v1 仅用于历史读取）；requirement_version为宿主给定版本；scope="ui-only"；windows数组。每项包含 id、name、independent、parent_window、anchor、controls、resources、deliveries。controls 包含 id、parent、type、image_mode（非图片为null）、sibling_index、anchor；resources 包含 id、owner_window、target_controls、generate、kind、size、slice_border（不适用为null）；deliveries 包含 id、phase、role、depends_on。控件引用使用窗口/控件完整编号；控件可见属性表承载完整布局，JSON不能与之矛盾。内部区域 independent=false、parent_window 指向独立窗口且 deliveries为空；对应控件归该窗口树，不重复定义。

下面仅演示一个窗口的交付标识，不是可代替完整文档的占位清单：

```json
{"schema_version":2,"requirement_version":"v1.0","scope":"ui-only","windows":[{"id":"W01","name":"登录窗口","independent":true,"parent_window":null,"anchor":"#window-W01","controls":[{"id":"W01/L00","parent":null,"type":"Panel","image_mode":null,"sibling_index":0,"anchor":"#control-W01-L00","name":"UILogin"}],"resources":[],"deliveries":[{"id":"W01-WHITEBOX","phase":"whitebox","role":"Prefab","depends_on":[]},{"id":"W01-ART","phase":"art","role":"Art","depends_on":["W01-WHITEBOX"]},{"id":"W01-ASSEMBLY","phase":"assembly","role":"Prefab","depends_on":["W01-WHITEBOX","W01-ART"]}],"prefab_name":"UILogin.prefab"}]}
```

资源 size 为 [width,height] 正整数像素；slice_border 为 [left,bottom,right,top] 非负整数，九宫格必须明确。image_mode 为 static、sliced 或 null。控件 type 使用 Panel、Image、TMP_Text、Button、ScrollRect、Viewport、Content 等明确类型。资源引用和父节点必须存在；唯一生产归属及跨窗口复用依赖不得成环。仅声明已决定内容，禁止以 TBD、空关键字段或示例值冒充定稿。

### 交付前一致性检查

使用同一份确定的定义生成可见清单和内嵌 JSON，修改任一处同步更新其余表现。检查 JSON 可解析、编号唯一、引用可解析、锚点实际存在、父子关系与绘制顺序一致、图片模式一致、窗口数量一致。当前独立窗口数 N 对应 3N 项交付，内部区域不增加任务；每一项明确对应窗口与阶段。Design 修复表达错误，实质边界问题返回初稿；缺项不得宣称可供准确拆分。

服务端第一阶段已实现 manifest v1 解析、引用与骨架结构校验。自然语言、线框与清单的完整语义一致性仍需 Design/PM 自检；未实际执行校验不能声称机器验证通过。

### v1 服务端校验补充

- 窗口 ID 使用 W 开头的大写字母、数字或连字符，长度 2～20；控件 ID 使用 窗口ID/局部ID。独立窗口对应唯一 section，独立窗口 section 不相互嵌套。内部区域锚点属于父窗口 section，controls/resources/deliveries 为空，其内容统一定义在所属窗口中。
- 每窗口只有一个 Panel 根；控件父引用不跨窗口、不成环，同父节点 sibling_index 不重复。Image 必填 static/sliced，其他控件 image_mode=null。
- resources 仅列图片资源；kind 使用 static/sliced。每个 Image 控件必须恰好映射一个资源；文本与容器不列图片。九宫格左右边距之和小于宽度，上下之和小于高度；static 的 slice_border=null。资源在唯一 owner_window 中定义，target_controls 列出所有复用位置。
- 跨窗口复用图片时，使用窗口的 assembly.depends_on 明确增加生产窗口的 Wxx-ART；本窗口白模和 Art 前置仍保留。不会增加任务数量。
- 每窗口阶段 ID 固定 Wxx-WHITEBOX、Wxx-ART、Wxx-ASSEMBLY，角色为 Prefab、Art、Prefab。schema_version 按命名规则输出 2，历史 v1 仍可读取；拒绝重复 JSON 字段与未知字段。当前单计划最多 33 个独立窗口（99 个子任务）。无清单的旧批准文档必须修订并重新审批，不静默迁移。

## UI 预制与节点英文命名（硬性规范，优先于旧编号展示）

- 每个独立窗口必须明确唯一最终预制文件名：`UI<功能英文PascalCase>.prefab`。例如登录为 `UILogin.prefab`，原因提示为 `UIReasonToast.prefab`。禁止使用窗口编号、任务编号、拼音或 GenericPanel 代替功能名。根 GameObject 名等于文件名去除 `.prefab`，白模与最终装配使用同一名称。
- 子节点用表达实际职责的标准英文 PascalCase，例如 `LoginBackground`、`TestIcon`、`Version`、`ServerDropdown`、`LoginButton`。禁止把 `S0`、`L01`、`B01` 等内部编号写入 GameObject.name，或用这些编号作为面向人的层级图、线框、属性表和路径名称。
- 节点树展示英文实际名称、中文释义和控件类型。绘制顺序另列“绘制顺序”属性或红字顺序图；不在名称前加 S0/S1 等前缀。按钮可见文案与 GameObject 名分别说明。路径由实际英文祖先名称组成，同父节点名称不得重复。
- 稳定机器 ID 只用于清单关联和锚点，不等于节点名；命名修订保留原 ID、父关系、层序和资源引用。读者主要内容不展示这些编码，不能为了美化展示破坏版本追踪。
- 新文档使用 `ui-delivery-manifest` schema_version=2：在 v1 原字段基础上，每个 windows 项增加 `prefab_name`（独立窗口必填上述文件名，非独立区域为 null）；每个 controls 项增加 `name`（真实英文节点名）。根 name 与预制文件名一致。v1 只用于读取既有历史版本，不再作为新文档输出格式。
- Design 自检所有线框、结构树、属性表、资源目标路径、可见预制名与清单 name/prefab_name 一致；PM 沿用名称，不另起；Prefab 参数明确设置 name 和输出文件名，不拿 id 代替 name。命名规则不授权重命名已经存在的 Unity 资产或破坏序列化引用。
