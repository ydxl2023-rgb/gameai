# 美术任务拆解

与 [PM主技能](../SKILL.md) 共同使用。只拆解已批准的资源范围，不新增业务规则，不自行派工或制作资源。

## 独立视图与状态（硬性规范）

- 拆解起点固定为批准文档3.1组件目录与3.2独立交互界面目录：每个组件定义恰好对应一张独立美术交付任务，每个独立交互界面恰好对应一张独立美术组装任务。禁止跨组件或跨界面合单，也不得仅创建一个“全部控件”任务。
- 用“组件编号 → 任务临时编号”和“界面编号 → 任务临时编号”逐项核对覆盖。任务标题包含中文组件／界面名称，source_refs精确引用对应图及属性表；不得遗漏无贴图但需要布局规范的滚动容器。
- 组件以目录中独立定义为边界：C01、R01、C02、UI-PANEL、UI-BUTTON、F01、UI-LIST分别成单。B01/B04等模板实例与内部文本、图片层归所属组件任务，不重复按实例建单；独立定义的新组件必须另建任务。
- V01、V02、V03、V04分别成单，任务列出实际使用的组件及依赖。V02加载、领取中和失败状态属于V02验收，不假造多个独立界面；独立浮层组件F01仍保留自己的组件任务。
- 界面组装与组件任务在同一计划中一起建单，按依赖控制启动，不能等组件完成后才补建界面任务。组件之间也按真实引用建立依赖，例如档位卡依赖道具框和所用按钮模板。通用容器只定义容器契约，不反向依赖使用它的具体卡片，避免循环。
- 对应程序任务同样禁止把多个独立界面塞进一张实现任务；存在运行行为的组件分别安排组件实现，再安排逐界面集成。纯静态资源不强造程序任务，QA按组件或界面交付范围覆盖并保留集成验收。

- 先逐张核对批准HTML中的线框及锚点，列出视图编号、用途、是否独立、所属组件、状态与交付标准。不能根据图的数量或同处一个章节直接合并任务。
- 可独立打开、布局或资源不同、可以分别验收的视图必须分别建立任务。六张独立线框至少对应六项视图交付，复用组件任务另外拆出；禁止用一个“入口与全部弹窗布局”任务覆盖它们。
- 同一视图的加载中、领取中、已领取、到期等状态若共享布局与资源，归入该视图任务的状态验收，不机械生成重复资源任务。新增独立反馈窗口、独立资源或独立验收结果时再单独拆分。
- 一个任务只拥有一个独立视图的组装，或一个目录组件的资源生产。组件内部图层与状态可同单交付，不得用“紧密相关”将目录内不同组件合并。

## 复合视图与资源层级（硬性规范）

- 逐层识别“视图 → 容器 → 组件实例 → 资源层”，为各层保留稳定编号。底板、滚动列表、档位框体、道具框、按钮、文字与状态标识不能混为一张平面截图交付。
- 有独立复用价值或可独立验收的底板、档位框体、按钮资源等拆为组件任务；每个组件任务包含自身必要图层，不机械地一图层一任务。
- 道具框四层必须为背景、图标、文本、框体，二维生产关联 [art-2d-itembox](../../gameai-art/art-2d/art-2d-itembox/SKILL.md)。其他组件按实际线框定义层级，不强行套用道具框四层；动态文字保留独立文本占位和排版约定。
- 滚动列表的美术交付是容器布局、裁剪区、间距、单元样式及状态资源映射；滑动逻辑、数据绑定和触屏交互归程序任务。不能让美术以静态图假装运行组件完成。
- 多个同类框体在源线框中未明确容器、滚动方向或一屏容量时，按文档格式规范列为策划线框缺口，返回策划修订；PM不得默认静态排列或自行改变方向。本次七日登录的档位必须按横向滚动列表拆解容器、档位组件与视图组装。
- 视图组装任务引用组件版本、实例位置与层级，在依赖完成后启动，交付最终分层布局和合成效果。组装不重复生产共享资源。
- 资源尺寸从批准文档和组件专项规范确定；128×128只用于道具框，不把整页底板或滚动列表缩成128×128。

## 视图2拆解示例

按原文实际存在的资源拆分，下列临时标识仅用于说明，不能伪造正式任务编号：

1. `ART-PANEL`：活动底板与独立装饰资源。
2. `ART-TIER`：档位框体及其可复用状态样式。
3. `ART-LIST`：通用裁剪滚动容器的布局契约；具体档位内容在视图组装时绑定，不反向依赖档位卡。
4. `ART-BUTTON`：文本按钮模板；关闭、领取等实例在界面中绑定名称和动作。其他独立定义的控件各自建单。
5. `ART-VIEW02`：组装视图2，依赖底板、列表、控件及实际使用的共享道具框。

其余独立视图分别建立组装任务，仅依赖它们实际使用的资源。图标、装饰、特效、动画和音效按批准范围及专业另行拆分；未要求的资源不扩充。

## 单据与交付映射（硬性规范）

- source_refs第一项必须是本任务交付对象的精确HTML锚点；组件任务指向自身组件图，界面任务指向自身界面图。其余引用仅为复用／上下文。不得让所有任务的第一项都指向全需求、共享总表或同一张无关图。Track按第一项定位主要线框，正文范围和验收标准仍须逐任务独立编写。

- 每张任务HTML直接展示所负责的线框或组件局部图，并标注“上下文”和“本任务负责范围”。引用整页作为上下文不代表负责整页全部资源。
- 单据至少列出视图编号、组件编号、层编号、资源用途、尺寸与透明要求、独立文件、实例映射、共享来源和验收条件；同组件在多视图使用时只生产一次。
- 交付文件统一存放仓库相对路径 `deliveries/<平台真实任务编号>/`，图层与合成效果分开保存。未发布计划以占位路径说明，待宿主映射真实编号；禁止继续使用需求编号代替任务交付目录名。
- 原始线框是构图与层级依据，最终资源必须落实本任务负责的视觉内容；只有线框截图、HTML或预览而没有约定的独立资源，不算资源生产完成。框体、图标与文字不得烘焙成唯一扁平图替代分层文件。
- `source_refs` 精确到批准HTML锚点及组件／层编号；资源层级、输出文件和验收条件写入既有 `description`、`acceptance`，不擅自新增宿主schema字段。

## 顺序、依赖与复核

- 共享资源 → 组件容器 → 视图组装 → 使用该视图的程序实现 → 对应QA。允许不依赖这些资源的程序逻辑独立推进，不建立虚假的全角色串行依赖。
- 真正的前置关系同时写入 `depends_on`，正文注明前置资源及版本；页组装验收核对每项资源映射、层序、状态、触屏布局和可读性。
- 发布前检查每张独立线框都有所属视图任务、每个独立组件都有唯一生产者、每个实例都有映射，没有资源遗漏或重复生产。不能只以任务数量或“六张图已覆盖”作为通过依据。
- 已发布计划重新拆分时先输出旧任务到新视图／组件的映射，保留已有交付与执行记录；不得直接删除已完成任务或复用其编号表示不同的新范围。
