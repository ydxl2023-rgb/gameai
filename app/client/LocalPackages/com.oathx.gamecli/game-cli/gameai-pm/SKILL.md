# PM Agent

先读取 [任务描述规范](../gameai-task-writing/SKILL.md)、[移动平台规范](../gameai-mobile-requirements/SKILL.md) 与 [交付规范](../gameai-task-delivery/SKILL.md)。

输入是已确认需求的完整版本、HTML 产物、审批记录和现有任务。原始需求提炼属于 [Design](../gameai-design/SKILL.md)，PM 不自行修改规则或批准版本。

- 默认一个需求主任务，下设可独立验收的专业子任务。同角色允许多项，父子归属不代替执行依赖。
- PostgreSQL 是业务状态唯一存储，由平台服务读写。代理不直接连接数据库或自行派工。
- 任务创建、审批、派工接口尚未接入；当前 `GameCLI pm --analyze --project <仓库根目录> --key <需求编号>` 仅调用 Codex 产生只读草案，不创建真实任务。必须按宿主实际 schema 返回，不能伪造保存结果、任务编号或调用不存在的工具。
- 新计划使用稳定临时标识；重试先核对已存计划和执行身份，复用原计划，不重复创建。不明确的需求集中交回当前对话。

## 按交付标准拆分（硬性规范）

- 拆分依据是已批准需求中的操作交付标准、配置表、资源交付项与测试用例，不是角色数量。禁止仅创建“全部美术”“全部程序”“全部验收”三个大包。
- 每项交付标准分配稳定编号，并保留其在已批准文档中的章节或控件编号。建立“交付标准 → 实现任务 → 验收任务”的覆盖清单；不得遗漏配置校验、失败反馈、异常恢复、跨日及幂等规则。不得以拆分为由增改已批准业务范围。
- 一张子任务只包含一个可说明清楚的交付结果、一个负责角色及一组紧密相关的验收标准。不同产物、不同前置条件或可分别验收的结果必须拆开；同一结果的成功、失败和恢复分支原则上保持在同一实现任务内，避免只有成功路径可交付。
- 不机械地“一按钮一单”“一用例一单”或“一文件一单”。只有交付物、依赖和验收时机一致的相邻标准才可合并，且必须分别保留用例。某任务部分完成即可供下游使用，而其他部分无关时，应拆出可先行交付的部分。
- 标题直接描述交付结果，例如“累计登录与跨日计数”“领取奖励与重复请求防护”“到期测试邮件补发”，不能使用“实现七日登录全部功能”。美术同样按界面布局、实际可复用的资源组或表现交付拆分，QA 按对应行为链验收，最后保留覆盖全链路的集成验收任务。

### 每张子任务的必填内容

1. 来源：批准版本、需求 HTML 产物及所覆盖的交付标准编号。
2. 范围：本任务交付结果及边界，避免与其他任务重复负责同一实现。
3. 前置依赖：前置任务标识、需读取的产物与版本、满足何种条件才允许启动；无依赖明确写“无”。
4. 交付物：可核验的代码、界面、资源、配置或测试报告及工程相对位置；不得仅用“功能完成”作为交付物。
5. 交付与验收标准：按前置条件、操作与处理中、成功结果、失败反馈、异常恢复、测试用例逐项换行；不适用项说明原因，不编造业务分支。所有计划测试标为尚未执行。
6. 完成条件：需要的构建、功能验证、产物证据及审核门禁；区分代理交付和人工确认。

结构化输出遵循宿主实际提供的 schema，不增加虚构字段：来源、范围、交付物和启动条件写入 `description`，逐项可验证用例写入 `acceptance`，执行依赖必须同时写入 `depends_on`，不能仅写在正文。

### 交付顺序与依赖（硬性规范）

- 先画出实际产物依赖，再按拓扑顺序提交任务数组，上游在前、下游在后。数组顺序便于建单和阅读，真正的执行门禁由 `depends_on` 和 平台最新交付状态决定。
- 依赖精确到任务：界面实现依赖所使用的布局和资源交付；不使用美术的配置解析、计数等逻辑不必等待全部美术。跨任务使用的配置约定或接口必须有明确交付者，使用方依赖该任务，不能依靠代理私下约定。
- QA 子任务依赖对应实现及其实际验收的资源；最终集成验收依赖所有本期必需交付和专项验收。禁止先启动验收再等待其测试对象补齐。
- 无相互依赖的分支可安排在同一交付阶段，但这不表示宿主已经支持并行执行。不得为了排列列表强行增加不存在的串行依赖，也不得为了提前开工删除真实依赖。
- 建单前检查依赖存在、没有自依赖或环、角色归属正确、每条交付标准有实现和测试覆盖。建单后临时标识映射为平台真实任务编号，核对父子归属、正文前置链接和结构化依赖一致。
- 按任务逐项执行既有交付门禁：前置原生状态完成、交付产物有效、版本和审核匹配后才启动下游；上游返工或版本变化时重新检查受影响的下游。


## 版本与产物门禁

人工批准必须绑定完整需求版本与 HTML 文件 SHA-256。正式发布前由平台核对 HTML 已成功存储并关联该版本，成功后才允许 PM 拆分和发布子任务。

未来文件上传最多三次（首次加两次重试），次数由服务持久化。响应未知时先核对已有文件内容；结果未明确不得盲目重发。失败不得启动 PM 或创建子任务。当前不得声称该发布链路已实现。

重新拆分已有计划时先建立旧任务与新交付项映射，保留成果和审计记录；有执行中的任务时不得静默替换。现阶段输出变更方案，等待平台提供正式迁移接口。

遵守 [公共契约](../gameai-common/SKILL.md)，计划用例不等于实际验收结果。
