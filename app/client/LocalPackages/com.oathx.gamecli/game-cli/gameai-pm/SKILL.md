# PM Agent

先读取 [任务描述规范](../gameai-common/gameai-task-writing/SKILL.md)、[移动平台规范](../gameai-common/gameai-mobile-requirements/SKILL.md) 与 [交付规范](../gameai-common/gameai-task-delivery/SKILL.md)。

输入是已确认需求的完整版本、HTML 产物、审批记录和现有任务。原始需求提炼属于 [Design](../gameai-design/SKILL.md)，PM 不自行修改规则或批准版本。

包含界面或美术交付时必须读取 [美术任务拆解](pm-art-breakdown/SKILL.md)，按独立视图、复用组件与实际图层建立资源映射和依赖，禁止把多个独立线框打包成一个布局任务。

- 默认一个需求主任务，下设可独立验收的专业子任务。同角色允许多项，父子归属不代替执行依赖。
- PostgreSQL 是业务状态唯一存储，由平台服务读写。代理不直接连接数据库或自行派工。
- 当前 `GameCLI pm --analyze --project <仓库根目录> --key <需求编号>` 保持只读草案。已批准需求可由人工在 Track 点击“PM 拆分任务”：云端校验已保存 HTML 和批准版本，调用 `GameCLI pm plan` 启动固定 PM，核验结果后原子发布主任务、美术、程序与 QA 子任务及依赖。PM 仅输出计划，不能伪造保存结果、真实任务编号或自行写库。
- 新计划使用稳定临时标识；重试先核对已存计划和执行身份，复用原计划，不重复创建。不明确的需求集中交回当前对话。

## 按交付标准拆分（硬性规范）

- 对含组件与界面的需求，3.1每个独立组件定义单独建任务，3.2每个独立交互界面单独建组装任务。先核对两份目录逐项覆盖，再按实际组件引用填写depends_on；不同组件、不同界面禁止合成一个任务，详细要求见美术任务拆解技能。

- 拆分依据是已批准需求中的操作交付标准、配置表、资源交付项与测试用例，不是角色数量。禁止仅创建“全部美术”“全部程序”“全部验收”三个大包。
- 每项交付标准分配稳定编号，并保留其在已批准文档中的章节或控件编号。建立“交付标准 → 实现任务 → 验收任务”的覆盖清单；不得遗漏配置校验、失败反馈、异常恢复、跨日及幂等规则。不得以拆分为由增改已批准业务范围。
- 一张子任务只包含一个可说明清楚的交付结果、一个负责角色及一组紧密相关的验收标准。不同产物、不同前置条件或可分别验收的结果必须拆开；同一结果的成功、失败和恢复分支原则上保持在同一实现任务内，避免只有成功路径可交付。
- 不机械地“一按钮一单”“一用例一单”或“一文件一单”。只有交付物、依赖和验收时机一致的相邻标准才可合并，且必须分别保留用例。某任务部分完成即可供下游使用，而其他部分无关时，应拆出可先行交付的部分。
- 标题直接描述交付结果，例如“累计登录与跨日计数”“领取奖励与重复请求防护”“到期测试邮件补发”，不能使用“实现七日登录全部功能”。美术同样按界面布局、实际可复用的资源组或表现交付拆分，QA 按对应行为链验收，最后保留覆盖全链路的集成验收任务。

### 每张子任务的必填内容

1. 来源：批准版本、需求 HTML 产物及所覆盖的交付标准编号。
2. 范围：本任务交付结果及边界，避免与其他任务重复负责同一实现。
3. 前置依赖：前置任务标识、需读取的产物与版本、满足何种条件才允许启动；无依赖明确写“无”。
4. 交付物：可核验的代码、界面、资源、配置或测试报告及工程相对位置；不得仅用“功能完成”作为交付物。
5. 交付与验收标准：按前置条件、操作与处理中、成功结果、失败反馈、异常恢复、测试用例逐项换行；不适用项说明原因，不编造业务分支。所有计划测试标为尚未执行。
6. 完成条件：需要的构建、功能验证、产物证据及审核门禁；区分代理交付和人工确认。

结构化输出遵循宿主实际提供的 schema，不增加虚构字段：来源、范围、交付物和启动条件写入 `description`，逐项可验证用例写入 `acceptance`，执行依赖必须同时写入 `depends_on`，不能仅写在正文。

### 任务详情阅读顺序与来源定位（硬性规范）

- 正文标签必须使用二字或四字名称，同一区域优先统一为四字，固定标签列宽并对齐冒号与正文；正文换行保持在内容列。统一使用“操作处理”，禁止写“操作与处理”。
- 单据顶部用紧凑的一行呈现派发入口、状态、需求版本、Agent、依赖；窄窗口允许自然换行，不把这些信息逐项排成竖向说明。
- 正文固定顺序：任务说明与范围 → 关联原始线框 → 交付内容与六项交付标准。执行结果单独呈现，不混入原始范围。规则仍为红字。
- `description` 按“需求来源：”“任务范围：”“任务依赖：”“交付内容：”“启动条件：”“完成条件：”分段，每段独占一行；交付物和完成条件放入最终交付区，禁止把整页 HTML 或 JSON 写进正文。
- `source_refs` 必须包含批准版本的相对 HTML 路径及真实线框锚点（如 `app/desgin/…html#reward-layers`），同时列出本任务相关页面／组件编号（如 P02、R01）。不能只写“第三节”或泛称原需求；锚点和编号必须能在源 HTML 中定位。
- 组件任务同时引用组件所在页面与分层图；页面任务只引用相关页面；反馈任务引用成功／失败视图。所有关联图按源文档逻辑顺序单列展示，不能并排。不涉及界面的任务明确说明原因；相关图缺失须注明缺口，不能用无关图冒充。
- 单据关联必须绑定拆分时批准的需求版本与哈希，禁止读取同名需求的最新版本替代。宿主当前可按这些引用在 Track 详情中展示原始线框；独立任务 HTML 的自动保存和关联仍须单独实现。

### 任务 HTML 与线框（硬性规范）

- 拆分后的每张专业任务必须有独立、离线可读的 HTML 单据，按 [文档输出规范](../gameai-common/gameai-document-format/SKILL.md) 排版；任务目录链接对应 HTML，不能仅交付总计划、JSON 或长文本替代任务单据。
- 单据包含任务标识、角色、需求版本与源 HTML 哈希、来源章节／控件、范围、前置产物与依赖、交付物、六项交付标准、完成门禁及真实审批状态。依赖链接打开对应任务单据；未发布使用临时标识，不伪造正式编号。
- 美术任务必须直接嵌入所负责的可见线框：布局任务展示相关页面，组件任务展示组件及分层图，表现任务展示触发控件与反馈状态。奖励道具展示背景、图标、文本、框体四层及稳定层编号，与本任务资源交付逐项映射。仅写“参考需求图”或给一个外部链接不算完成。
- 程序界面任务和对应 QA 单据同样嵌入相关线框；纯逻辑、配置或接口任务展示关联交互线框并明确其为上下文、不属于界面制作范围，无任何界面的任务注明原因并展示真实输入输出／流程示意，不能虚构游戏页面凑图。
- 从批准的原始需求复用线框或截取相关组件，保留编号与含义，不擅自改规则或扩充资源范围。按操作顺序单列排列，规则红字，正文与线框范围一致。源文档缺少必需线框时先列出缺口，不把任务标为完整。
- 当前宿主仍接收既有结构化计划 schema；HTML 是由宿主保存并关联的阅读产物，不把整页 HTML 塞进 `description` 或自行增加 schema 字段。正式建单流程必须实现每张任务的 HTML 产物保存和关联后，才可声称符合本规范；仅改技能不代表平台自动生成已接通。
- 只读预演可由宿主先生成本地 HTML 单据，状态明确为未审批、未发布。生成单据不授予上传、建单或派发权限。

### 交付顺序与依赖（硬性规范）

- 先画出实际产物依赖，再按拓扑顺序提交任务数组，上游在前、下游在后。数组顺序便于建单和阅读，真正的执行门禁由 `depends_on` 和 平台最新交付状态决定。
- 依赖精确到任务：界面实现依赖所使用的布局和资源交付；不使用美术的配置解析、计数等逻辑不必等待全部美术。跨任务使用的配置约定或接口必须有明确交付者，使用方依赖该任务，不能依靠代理私下约定。
- QA 子任务依赖对应实现及其实际验收的资源；最终集成验收依赖所有本期必需交付和专项验收。禁止先启动验收再等待其测试对象补齐。
- 无相互依赖的分支可安排在同一交付阶段，但这不表示宿主已经支持并行执行。不得为了排列列表强行增加不存在的串行依赖，也不得为了提前开工删除真实依赖。
- 建单前检查依赖存在、没有自依赖或环、角色归属正确、每条交付标准有实现和测试覆盖。建单后临时标识映射为平台真实任务编号，核对父子归属、正文前置链接和结构化依赖一致。
- 按任务逐项执行既有交付门禁：前置原生状态完成、交付产物有效、版本和审核匹配后才启动下游；上游返工或版本变化时重新检查受影响的下游。


## 版本与产物门禁

人工批准必须绑定完整需求版本与 HTML 文件 SHA-256。正式发布前由平台核对 HTML 已成功存储并关联该版本，成功后才允许 PM 拆分和发布子任务。

未来文件上传最多三次（首次加两次重试），次数由服务持久化。响应未知时先核对已有文件内容；结果未明确不得盲目重发。失败不得启动 PM 或创建子任务。现已支持已入库且已批准 HTML 的手动 PM 发布链路；自动派工与新上传重试编排仍属于后续阶段。

重新拆分已有计划时先建立旧任务与新交付项映射，保留成果和审计记录；有执行中的任务时不得静默替换。现阶段输出变更方案，等待平台提供正式迁移接口。

遵守 [公共契约](../gameai-common/SKILL.md)，计划用例不等于实际验收结果。

## 开发阶段的手动发布

- 生成 Art、Development、QA 子任务，均以交付标准为单位。QA 必须依赖具体 Development 交付；服务会为遗漏验收的程序任务补充 QA。六项交付与验收标准和测试用例写进每张任务。
- `pm plan` 返回 `summary`、`tasks`；任务包含 `id`、`title`、`role`、`description`、`source_refs`、`acceptance`、`depends_on`。`acceptance` 分为 `preconditions`、`steps`、`success`、`failure`、`recovery`、`tests`，不适用项解释原因。
- 同一批准版本重复点击复用既有记录，成功后禁止重复创建；失败可由人工重试，最多三次。状态未知或超时且原执行未核实时禁止重跑。
- 主任务由服务创建，不由代理在任务数组中重复创建。依赖只引用本计划的子任务临时编号；按实际资源依赖拆分，不把所有程序工作都阻塞在全部美术之后。
- 默认人工批准不自动调用 PM；当用户在审批确认中勾选“批准后自动执行”，云端记录该具体版本的授权，批准后调用固定 PM，发布后自动允许该计划专业子任务并按依赖推进。未勾选时保持手动 PM 和手动派发。已勾选任务可由人工开启同计划自动推进；跨机器 Worker 派工尚未实现。
