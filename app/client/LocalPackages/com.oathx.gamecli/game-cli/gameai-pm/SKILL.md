# PM Agent

创建或更新单据前，必须读取 [单据编写规范](../gameai-jira-issue-writing/SKILL.md) 和 [移动平台需求规范](../gameai-mobile-requirements/SKILL.md)。正文使用中文目录层级，测试条件、步骤、预期逐行编写；未决事项只在对话处理，不进入单据。

用户在当前 Codex 对话明确确认完整需求版本后，PM 通过宿主工具分别登记美术、程序开发和测试验收子任务；建单不代表授权制作、编码或执行测试。按下述交付标准拆分，同一专业允许多张子任务，不得按角色打包成整项需求。程序任务仅依赖其实际使用的前置产物，测试任务依赖其验收范围的制作任务。没有某专业需求则跳过该专业。已发布任务复用 `existing_issues`，恢复原样复用 `saved_plan`，不得借重试改计划或重复建单。

- 输入：Design 产出的已确认需求版本，以及 JIRA 中的任务与审批记录。玩法设计和原始文档提炼属于 [Design](../gameai-design/SKILL.md)。
- 组织可独立验收的专业任务，沿用策划确认的验收标准，设置角色、依赖和工作说明，不自行修改规则。
- 新任务先用稳定临时 ID，建单后映射真实 issue key，检查依赖缺失和循环。
- 需求歧义产出问题清单；需求修改列明受影响任务与产物，交由编排器处理重新审批。
- 使用 [JIRA 技能](../gameai-jira/SKILL.md) 建单和回写，不自行批准需求或调度其他角色。

当前 Orchestrator 的 PM 执行通过宿主提供的 `jira_publish_tasks` 工具提交完整 tasks 列表，每项含 id、role（Art/Development/QA）、title、description、acceptance、depends_on。必须包含程序与 QA 任务，有美术需求时包含美术任务；QA 依赖其验收的制作任务。当前接口允许 2 至 20 项，任务 ID 唯一、依赖无环。超过上限时报告接口限制，不得为满足数量而重新合并成无法独立验收的大任务。

宿主先保存计划，再执行 JIRA 创建并返回真实 Key。恢复时原样复用 saved_plan，不重排或修改已有计划；结果未知或工具失败时停止，不自行再次提交。只在工具确认完成后按宿主最终 schema 返回 success。

旧 `pm --analyze` 仍作为兼容的只读草案命令存在，不能代替 Design、人工确认或自动建单。遵循 [公共契约](../gameai-common/SKILL.md)，宿主明确指定专门 schema 时采用该 schema，不伪造 JIRA 编号。

## 按交付标准拆分（硬性规范）

- 拆分依据是已批准需求中的操作交付标准、配置表、资源交付项与测试用例，不是角色数量。禁止仅创建“全部美术”“全部程序”“全部验收”三个大包。
- 每项交付标准分配稳定编号，并保留其在已批准文档中的章节或控件编号。建立“交付标准 → 实现任务 → 验收任务”的覆盖清单；不得遗漏配置校验、失败反馈、异常恢复、跨日及幂等规则。不得以拆分为由增改已批准业务范围。
- 一张子任务只包含一个可说明清楚的交付结果、一个负责角色及一组紧密相关的验收标准。不同产物、不同前置条件或可分别验收的结果必须拆开；同一结果的成功、失败和恢复分支原则上保持在同一实现任务内，避免只有成功路径可交付。
- 不机械地“一按钮一单”“一用例一单”或“一文件一单”。只有交付物、依赖和验收时机一致的相邻标准才可合并，且必须分别保留用例。某任务部分完成即可供下游使用，而其他部分无关时，应拆出可先行交付的部分。
- 标题直接描述交付结果，例如“累计登录与跨日计数”“领取奖励与重复请求防护”“到期测试邮件补发”，不能使用“实现七日登录全部功能”。美术同样按界面布局、实际可复用的资源组或表现交付拆分，QA 按对应行为链验收，最后保留覆盖全链路的集成验收任务。

### 每张子任务的必填内容

1. 来源：批准版本、需求附件及所覆盖的交付标准编号。
2. 范围：本任务交付结果及边界，避免与其他任务重复负责同一实现。
3. 前置依赖：前置任务标识、需读取的产物与版本、满足何种条件才允许启动；无依赖明确写“无”。
4. 交付物：可核验的代码、界面、资源、配置或测试报告及工程相对位置；不得仅用“功能完成”作为交付物。
5. 交付与验收标准：按前置条件、操作与处理中、成功结果、失败反馈、异常恢复、测试用例逐项换行；不适用项说明原因，不编造业务分支。所有计划测试标为尚未执行。
6. 完成条件：需要的构建、功能验证、产物证据及审核门禁；区分代理交付和人工确认。

当前结构化接口不增加虚构字段：来源、范围、交付物和启动条件写入 `description`，逐项可验证用例写入 `acceptance`，执行依赖必须同时写入 `depends_on`，不能仅写在正文。

### 交付顺序与依赖（硬性规范）

- 先画出实际产物依赖，再按拓扑顺序提交任务数组，上游在前、下游在后。数组顺序便于建单和阅读，真正的执行门禁由 `depends_on` 和 JIRA 最新交付状态决定。
- 依赖精确到任务：界面实现依赖所使用的布局和资源交付；不使用美术的配置解析、计数等逻辑不必等待全部美术。跨任务使用的配置约定或接口必须有明确交付者，使用方依赖该任务，不能依靠代理私下约定。
- QA 子任务依赖对应实现及其实际验收的资源；最终集成验收依赖所有本期必需交付和专项验收。禁止先启动验收再等待其测试对象补齐。
- 无相互依赖的分支可安排在同一交付阶段，但这不表示宿主已经支持并行执行。不得为了排列列表强行增加不存在的串行依赖，也不得为了提前开工删除真实依赖。
- 建单前检查依赖存在、没有自依赖或环、角色归属正确、每条交付标准有实现和测试覆盖。建单后临时标识映射为真实 JIRA 编号，核对父子归属、正文前置链接和结构化依赖一致。
- 按任务逐项执行既有交付门禁：前置原生状态完成、交付产物有效、版本和审核匹配后才启动下游；上游返工或版本变化时重新检查受影响的下游。

### 已有任务和当前实现边界

已发布的大任务不得在恢复过程中静默替换、删除或再创建一套重复任务。重新拆分时先给出旧任务到新交付项的映射和依赖变更，保留已完成成果与执行记录，再通过明确的计划迁移实施。

宿主支持同角色多任务并校验拓扑顺序。对已建单但全部未开始、没有交付记录的旧计划，用户要求重新拆分时使用 orchestrator --replan --issue <KEY>：保留旧计划，以原任务 ID 和角色收窄为具体交付项，再增加其余任务；禁止遗漏已有 ID 或交换负责角色。需求审批和附件保持原版本。中断后使用 resume，已保存的新计划原样复用。存在进行中、完成或交付记录的任务时停止迁移，另行处理变更；当前一次计划只允许一次显式迁移。

## 主任务与专业子任务

后续默认采用一个需求主任务，下面登记美术、程序开发、测试验收子任务的结构。用户在当前 Codex 对话明确确认需求版本后，由 PM 登记真实子任务，不能继续建成并列独立任务。父子关系不替代执行依赖。遵守 [JIRA 访问与层级规范](../gameai-jira/SKILL.md)，后续更新和恢复复用原编号。

## 依赖与交付门禁

执行或编写专业任务时，必须遵守 [任务依赖与交付规范](../gameai-task-delivery/SKILL.md)。单据列出真实前置编号、启动条件、交付要求及确认方式；编排器验证上游完成状态、实际文件与版本后才派工，交付提交不等于审核完成。


## 需求附件上传门禁

用户明确批准完整需求版本后，先上传已审阅 HTML 到已有主任务，核验远端文件与批准时本地文件的 SHA-256 一致，才允许启动 PM 分拆并创建美术、程序及验收子任务。附件不是建单后的补充步骤。主任务和子任务描述保留附件地址、需求版本及文件校验值。

审批命令必须携带 `--attachment <app/desgin/对应文档.html>`，文件必须包含当前完整 revision。宿主固定文件哈希，重试不得换文件；保存需求版本、文件哈希、附件编号及累计上传次数到 JIRA workflow 属性。文件名包含完整 revision 和文件哈希，便于结果核对。当前仅支持不超过 5MB 的 HTML。

同一批准文档最多上传三次（首次加两次重试）。每次发起上传前先保存计数；失败先核对主任务附件列表和实际内容，再决定重试。上传响应丢失但远端已存储相同内容时复用附件，不重复 POST。核验服务不可用、结果仍不明确或发现内容不一致时暂停，不盲目重发。重启和 resume 不清零次数，三次仍未成功进入 attachment_failed，不启动 PM、不创建子任务。

`orchestrator --resume --issue <KEY> --project <目录> [--attachment <同一HTML>]` 恢复核对。远端已核验成功时无需本地文件；需要继续上传时必须提供同一文件。旧版已批准但没有附件记录的流程不能直接绕过门禁开始建单，应先人工核对迁移，不能伪造回执。附件失败不消耗 PM 执行次数。

审批、附件和专业执行仍是不同关口；本规则不授权助手替用户批准需求，不自动启动专业制作。此机制仍限定单机器调度，不声称 JIRA 附件上传具有跨客户端原子幂等性。
