# 纲要式文档输出规范

## 强制适用范围

以后 GameCLI 流程中向用户交付的文档统一采用用户提供的《全AI流程规划纲要.html》的阅读方式：独立 HTML、封面、可点击目录、编号章节、分层列表、表格与打印样式。需求草案、修订稿、最终稿、设计方案、开发说明和验收报告均适用。除非用户明确指定其他格式，不能仅交付 Markdown、纯聊天长文或原始 JSON 代替阅读文档。

这项要求限定用户阅读产物。标准技能仍使用 SKILL.md，CLI 与 Agent 仍遵守 JSON schema，JIRA 正文仍遵守单据编写规范，不向这些接口塞入整页 HTML。短答复和进度通知无需生成文档。

## 模板与排版

- 使用随技能分发的 [HTML 模板](assets/outline-template.html)，保留参考纲要的浅灰背景、居中白色页面、中文字体、封面、目录、标题分隔线、表格、提示框和打印按钮。模板不依赖原开发机器上的文件。
- 交付为 UTF-8 编码的单文件 HTML，样式内嵌，不依赖外部字体、脚本或网络才能阅读正文。允许保留真实参考链接。
- 封面显示中文标题、用途、日期、版本与真实状态；存在 JIRA 任务时附编号与链接。完整需求 revision 必须可查看，不用展示版本代替审批版本。
- 目录链接对应真实且唯一的章节锚点；正文采用 1、1.1 等连续编号，不强行照搬参考纲要的业务章节。根据文档类型组织调研依据、目标、范围、规则、界面、交付、依赖和验收等内容。
- 每条规则独立成行。比较和映射使用表格，流程可以使用内嵌图示；正文不能只展示摘要或原始结构化快照。
- 每个测试用例分为前置条件、操作步骤、预期结果，各项分行；保留尚未执行、实际通过或失败的真实标记。
- 标题与描述使用中文；字段名、代码标识符、路径、真实单据编号和链接保留必要原文。
- 窄窗口可读，长版本号与链接换行；打印时隐藏操作按钮并保留完整正文。禁止用固定高度或裁剪隐藏需求。

## 必须产出的界面线框布局图

最终需求文档（包括交给用户整体确认的最终审阅稿）必须包含第三节内独立的“界面线框布局”小节，并纳入可点击目录。这是系统必须产出的内容，不是可选配图。缺失实际线框图的文档不能声明完整、定稿或提交整体确认，不能用纯文字描述、流程图、“美术后续提供”或未渲染的图形代码替代。

- 绘制本需求涉及的入口、主要页面或弹窗及必要的辅助页面，标明页面名称、区域划分、信息层级、按钮和关闭/返回入口。多个视图必须沿纵向按操作逻辑排列，不能并排，也不能遗漏关键操作界面。
- 采用移动端触屏布局，使用简洁低保真方框、文字、占位图标和必要连线，不引入鼠标、悬停、右键等交互，不将线框当作正式美术资源。
- 每张图配中文图注，说明入口、操作、反馈和跳转目标。关键状态用状态小图或与图中控件对应的状态表展示，覆盖需求实际涉及的正常、不可操作、处理中、异常与完成状态，不凭空扩展功能。
- 线框内容必须与当前需求规则、字段、奖励档数和交互范围一致。新出现且改变业务语义的选择必须回到集中决策流程，不能借绘图擅自增加业务要求或绕过版本确认。
- 使用内嵌 SVG 或 HTML/CSS 绘制真实可见的线框，嵌入单文件 HTML；离线打开和打印均可见。不依赖外部图片链接、在线渲染服务或安装插件。SVG 提供 viewBox、中文标题或说明，保证文字清晰、不重叠、不裁切。
- 线框是用于确认布局和交互的低保真方案，图注标明这一性质；尺寸、字体、色彩或占位图标不能被误读为已批准的正式视觉规范。
- 不虚构不存在的界面。纯后台需求也必须保留本章节，明确说明没有玩家界面，并图示真实存在的操作或结果查看界面；确实无任何界面时说明不适用的具体原因，不能用空白占位图冒充线框完成。

交付前逐项核对：目录可跳转、图实际渲染、主要页面覆盖、控件与业务一致、关键状态可理解、窄窗口可读、打印不截断。设计内容和审批以对应 JIRA 版本为准；阅读副本中的线框不能承载未记录的新业务规则。
## 生成与交付

由当前对话宿主将 Agent 的结构化结果排版为 HTML。独立 Agent 无文件权限时仍返回规定的结构化内容，不能声称已经生成文件。模板中的占位标记必须全部替换；动态文本需 HTML 转义，输入资料不可作为脚本执行。

Design 需求文档必须按 [Design 文档存放规范](../gameai-design/SKILL.md) 输出到目标工程根目录的 `app/desgin/`，不存在时自动创建；保留该拼写，不再放入 `docs/`。其他工程说明仍可输出到 `docs/`。使用中文文件名。Markdown 可作为辅助维护源，但用户收到的主链接必须是 HTML 阅读版。生成后检查标题、目录锚点、完整内容、版本与审批状态、测试用例数量及占位符，并打开预览检查排版。

JIRA 仍是流程与审批唯一可信来源，HTML 是对应版本的阅读副本。格式转换不能改变业务要求、重新分析需求、批准版本或创建任务。当前对话给出简短摘要及 HTML 链接，不要求用户从聊天记录拼接完整文档。

## 需求文档四节结构与交互闭环

需求文档正文固定为四节，优先简短且可验收，不重复堆叠规则、开发清单和测试说明：

1. 设计目标：用简短段落说明玩家价值、目标和本期范围。
2. 功能综述：集中说明资格、期限、核心玩法、奖励及跨页面共用规则。
3. 界面与交互：先给实际线框图，为页面与控件编号，再描述每个按钮和信息区域。按玩家操作组织交付标准；静态元素使用“编号—显示内容—更新条件”表，不机械重复验收段落。
4. 美术与表现需求：按页面或交互列出界面、图标、特效、动画、按钮音效，注明用途、触发条件和本期交付状态（制作／占位／本期不需要）。这些类别必须逐项说明，不因有栏目就默认扩大资源制作范围。

调研来源、详细测试和技术说明放附录，可使用默认收起但打印展开的区域。正文必须保留核心规则与异常处理，不能为简短而遗漏要求。

每项玩家操作必须覆盖以下六项：
- 前置条件。
- 操作步骤与处理中反馈：触发入口、请求期间显示、能否重复操作。
- 成功结果与界面反馈：业务变化、弹窗或提示内容、后续按钮、相关状态更新。
- 失败原因与界面反馈：明确业务失败的原因、提示、可执行的下一步。
- 异常恢复处理：断线、超时、响应未知时的提示，权威状态查询、重试与防重复要求。响应未知不得直接视为业务失败。
- 测试用例：列出正常、失败及异常分支的可判定测试场景；完整用例仍按前置条件、操作步骤、预期结果分行，可移至附录引用，避免正文重复。

仅写“点击按钮”或“操作成功”不构成完整交互描述。无异步请求的关闭、返回操作说明本地导航结果；存在关闭动画时必须说明动画与实际关闭的先后关系，不得一律写为即时关闭，失败和网络处理可明确不适用及原因，不能虚构网络调用。线框必须覆盖需求实际采用的处理中、成功弹窗、失败提示及恢复操作，并与控件编号对应。成功反馈是否需要特效、动画和音效必须在第四节明确，不自行默认正式资源制作。

## 打开与关闭动画的硬性要求

凡需求包含界面打开或关闭动画，第三节对应操作的“操作步骤与处理中反馈”必须明确写出动画，不能只在第四节资源清单列出，也不能仅写“打开界面”或“关闭界面”。

- 打开操作：说明点击哪个入口、何时显示界面并播放哪个打开动画、动画与数据加载的先后或并行关系、播放期间允许哪些操作、何时进入可交互状态。
- 关闭操作：说明点击关闭／返回／确定后的关闭动画、播放期间是否允许重复操作，以及动画结束后何时隐藏当前界面或返回目标页面。不得在播放动画前就销毁需要展示动画的界面。
- 对涉及动画的操作，测试场景必须覆盖动画触发、播放期间的重复点击及结束后的正确界面状态；实际支持播放中关闭或切换时，补充对应中断行为。
- 操作中的动画名称或编号与第四节“美术与表现需求”一一对应，说明用途和触发条件。交互章节不得引用未列入交付范围的动画，资源章节也不能替代操作过程描述。
- 不需要动画时，操作步骤只描述真实的界面显示、隐藏及状态变化，不添加动画句子或“无动画”占位说明，不为满足模板自行新增动画。第四节仍按范围规则标明动画类别本期不需要。

交付检查必须逐项核对打开、关闭、返回和确定操作：存在动画却未写入操作过程，或操作过程与动画交付清单不一致，均视为文档不完整，修正后才能提交整体确认。

## 线框顺序排版的硬性要求

- 线框视图一律单列纵向排列，宽屏、窄屏和打印均禁止并排、双列网格和横向轮播。
- 按玩家操作逻辑排序：入口 → 主页面 → 操作处理与成功／失败反馈 → 辅助功能分支。图前标明页面、触发控件和返回目标。
- 独立分支注明从哪个页面进入，不能画成必须依次经历的操作。成功与失败标明互斥结果，不同时出现。
- 单一界面内部可保留真实的横向按钮或奖励卡布局；本规则禁止多个线框视图并排，不改变产品界面本身。
- 交付前检查文档顺序以及响应式和打印样式，模板与产出均须符合单列规则。

## 手机底框与设计画布

本项目后续手机线框统一使用1920×1080横屏设计画布，以带刘海的 iPhone 外观作为设备背景：左侧刘海、圆角屏幕、底部手势条，标示布局安全区域。所有界面在同一比例的屏幕内部展示，继续单列按操作逻辑排序。

该尺寸是用户指定的设计画布，不宣称它是某款手机的原生分辨率。安全区域仅作示意，运行时按设备实际安全区适配。文字、按钮及关键内容避开刘海和手势区域，不裁剪或遗漏控件。设备底框和辅助标记不属于实际游戏美术交付。

优先使用内嵌 SVG 的 viewBox 保持画布比例、清晰缩放与离线打印；标注画布尺寸。不得拉伸屏幕、改变比例或把多台手机并排排列。单个屏幕内的奖励卡等可按实际横屏布局排列。

绘图时使用随技能分发的 [横屏手机底框](assets/phone-landscape-frame.svg)，在内部1920×1080画布中替换示例内容。

## 配置表设计的必备内容

涉及可配置数据的功能，第三节必须在“操作交付标准”之前提供“Excel 配置表设计”小节，并纳入目录；相应后续编号顺延。说明工作簿名、工作表职责、每行含义、字段名、类型、必填性、主键／外键、单位或范围、示例值、完整性校验和错误处理。

区分固定业务规则、策划可配置数据与玩家运行数据，不把账号进度或审批状态写入配置表。说明配置加载和生效时机、已有账号快照或兼容策略，并给出可执行的最小示例及配置测试要点。不擅自增加业务可配范围，不将示例资源路径描述为真实存在。字段设计不等于已经生成工作簿或实现导入代码；如需实际工作簿另按用户授权产出。

### 配置字段的 C# 类型

字段类型必须使用标准 C# 类型表示，例如 `string`、`int`、`long`、`float`、`double`、`decimal`、`bool`，日期等使用明确的 .NET 类型如 `DateTimeOffset`，不得使用“文本”“整数”“数字”等泛称代替类型。集合明确元素类型，如 `int[]`；可空类型明确标注，如 `int?`。根据实际语义选型，不为统一而改变原有数值范围。必填性、默认值、单位、范围和 Excel 单元格的填写／解析格式单独说明，不能混同为字段类型。字符串非空约束仍需独立校验。

### 奖励引用必须使用列表

奖励引用字段默认且必须使用一个列表字段（例如 `Rewards`），一条配置即可承载一次发放的多个奖励。即使只有一种奖励也使用单元素列表，不退化为单个道具字段，不用同档多行或 Reward1/Reward2 等列替代奖励列表。奖励档位一行一条，列表顺序即展示顺序。

配置类型栏的命名元组采用用户约定的 `List<(int:ItemId,int:Number)>` 形式；这是配置类型标记，不是可直接编译的 C# 语法。对应代码类型为 `List<(int ItemId, int Number)>`。填表使用外层列表大括号、内层条目大括号，元素顺序与类型声明严格一致。声明字段数与每项实际值数量必须相同；不推断未定义的第三项含义。字段数量、顺序或含义有矛盾时先集中澄清再定稿。

校验整份奖励列表的语法、元组长度、各项类型、道具引用及正数数量后才能发放；同一次奖励请求使用统一幂等约束，不能重试时重复发放已成功的条目。领取成功窗口和补发记录展示实际奖励列表。文档须区分配置语法、Excel 单元格写法与生成后的 C# 类型。

用户已确认奖励元组固定为两项：`ItemId`、`Number`，均为 `int`。固定配置类型为 `List<(int:ItemId,int:Number)>`，C# 类型为 `List<(int ItemId, int Number)>`。标准填表示例 `{{40,8},{10,6}}` 表示道具40发8个、道具10发6个；单项也使用 `{{40,8}}`。不允许第三项或自行引入奖励类型。奖励字典的道具主键也必须是 `int`，数量为正整数。每档一行，一个 `Rewards` 列表保存本次全部奖励，列表顺序作为展示顺序。
