# 任务依赖与交付

本技能只规定交付门禁，不定义玩法、美术风格或编码细节。JIRA 是依赖、审批、执行和交付版本的唯一可信来源；本地只保存实际文件与证据。

## 顺序与职责

- PM 按 [交付标准拆分规范](../gameai-pm/SKILL.md) 建立任务级依赖图，同一专业可有多张子任务。使用美术产物的程序任务遵循“所需美术交付并抽检完成 → 对应程序交付并校验完成 → 对应测试验收 → 用户最终验收”；不使用美术的逻辑任务无需等待无关美术。最终集成验收汇合全部必要交付与专项验收，不增加程序人工审批。
- 项目管理负责建立主任务、专业子任务和 `depends_on`；编排器负责核验和启动代理。父子归属不能代替依赖。
- 需求确认前只保留需求主任务，不创建专业子任务；用户确认后由 PM 建单，执行前必须有当前版本的需求审批及已发布计划。不能把创建单据解释为批准执行。
- 每次启动读取最新 JIRA，所有前置子任务必须属于同一需求，原生状态类别为完成，交付清单有效，实际文件存在且哈希一致，证据齐全。
- 上游重新打开、文件变化、需求修订或交付版本替换后，下游原交付失效；不能凭旧的完成状态继续放行。

## 专业交付

- 美术：符合任务范围的界面设计、布局尺寸、触屏交互说明、资源及预览、导入要求。程序先读取这些文件，再实现界面；不可用文字猜测替代美术交付。
- 程序：实际修改的代码与界面资源、构建和功能检查报告，记录所使用的美术版本。遵守工程编码规范，保留用户修改。
- 验收：对指定程序和美术版本逐项验证验收标准，给出真实日志、截图或报告。未运行、失败或证据缺失不能报告通过。
- 宿主指定结构时返回 `verdict`（`pass`、`fail`、`blocked`）、中文 `summary`、`artifacts`、`checks`。
- 每个产物包含工程相对 `path`、实际小写 `sha256`、中文 `purpose`；包含真实成果和验证报告，不得只交付一份自称完成的说明。
- 每项检查包含中文 `name`、真实 `passed`、指向本次产物的 `evidence_path`。宿主验证文件完整性；哈希正确不等于视觉、玩法或测试结论正确。
- 缺少生成工具、运行环境或无法验证时明确阻塞，不能用占位图、空文件或编造报告冒充最终交付。

## 执行与审核

- `orchestrator --gates --issue <主任务> --project <工程> --format json` 只读检查依赖与交付。
- `orchestrator --dispatch --issue <主任务> --project <工程> --format json` 启动符合门禁的专业代理；读取上游交付并记录输入版本。逐项串行执行，遇到审核或阻塞停止；`--watch` 在后续通知到达后重新核对。
- 专业代理可在当前工程内使用本地工具制作和验证，不能修改上游产物、操作 JIRA、批准任务、提交推送或启动其他代理。默认禁用继承的外部工具；需要的工具不可用则返回阻塞。
- 提交前再次核对审批、执行身份和上游版本，防止运行期间发生的变更被忽略。
- 交付写入子任务属性 `gamecli.delivery.v1`，对应子任务评论展示中文执行结果，需求描述不被执行结果覆盖。宿主计算交付版本并校验实际文件；代理自己不能批准需求、抽检或最终验收。
- 美术保留原纲要中的人工抽检，用户核对实际文件与版本后在 JIRA 完成美术子任务。再次调度即可开始程序；程序通过交付校验后，由编排器使用项目真实工作流中唯一可用的完成转换回写并继续启动验收，不等待额外人工程序审批。
- 完成转换前持久化 `completion_requested`。响应丢失时先读取原生状态；已完成则继续，未确认时阻塞而不重复转换。没有唯一可用完成转换、缺少字段或权限时明确报错，不猜测状态名称或转换编号。
- 验收提交后保留最终人工验收，由用户完成验收子任务；不能由代理自批、合并或发布。
- 重跑前先重新打开相应子任务。失败或失效任务使用 `--dispatch ... --retry-task <子任务编号>`，最多三次。处于运行中的记录不允许自动重试，先核实原进程和远端副作用；不直接删除记录规避保护。
- 提交响应丢失时重新读取 JIRA 交付属性；不能因为本地没收到结果就再次启动。当前限定同一工程单机器、单用户调度，文件锁不具备跨机器互斥能力。

描述按 [单据编写规范](../gameai-jira-issue-writing/SKILL.md) 展示前置依赖、启动条件、交付要求、确认方式和真实检查结果，禁止把计划用例标为已执行。

每次专业执行的成功、阻塞、失败或取消结果必须由编排器写入对应 JIRA 子任务评论，包含执行编号、角色、会话、结果与证据。评论不得把代理报告误写成人工批准；真实状态和版本仍由交付属性核对。发送结果未知时保留 JIRA 中的评论投递意图，核对已有评论后再恢复，不能重复投递或启动同一次执行。
